# 格式化生成：Output Parsers、LlamaIndex 与 Function Calling 比较

> 依据《第五章 生成集成 第一节 格式化生成》整理，重点比较格式化生成的应用场景、实现方法、LangChain Output Parsers、LlamaIndex 输出解析、不依赖框架的实现思路，以及 Function Calling 的工作流程与优势。

## 一、为什么需要格式化生成

| 应用场景 | 需求 | 期望输出形式 |
|---|---|---|
| RAG 驱动的电商客服 | 用户询问“推荐几款适合程序员的键盘” | 包含产品名称、价格、特性、购买链接的 JSON 列表，便于前端渲染商品卡片 |
| 自然语言转 API 调用 | 用户说“帮我查一下明天从上海到北京的航班” | 结构化 API 请求，如 `{"departure": "上海", "destination": "北京", "date": "2025-07-18"}` |
| 数据自动提取 | 从新闻文章中抽取事件、时间、地点、人物 | 结构化数据，存入数据库 |
| 核心价值 | 连接 LLM 的自然语言理解能力与下游应用程序的程序化逻辑 | 让模型输出具有特定结构的数据，如 JSON 或 XML |

## 二、格式化生成实现方法比较

| 方法 | 核心思想 | 优点 | 缺点/注意 | 代表工具 |
|---|---|---|---|---|
| LangChain Output Parsers | 在 Prompt 中自动注入格式指令，将 LLM 返回的纯文本解析成结构化数据 | 开箱即用，解析器丰富，支持严格验证 | 依赖框架，解析失败会抛异常 | `StrOutputParser`、`JsonOutputParser`、`PydanticOutputParser` |
| LlamaIndex 输出解析 | 与生成过程紧密结合，通过响应合成和结构化输出实现 | 与 RAG 流程集成好，优先使用 Function Calling | 依赖框架，灵活性受框架限制 | 响应合成器、Pydantic Programs |
| 不依赖框架的简单实现 | 通过提示工程技巧引导模型输出 JSON | 灵活，不依赖框架 | 可靠性依赖提示设计，可能需要语法约束 | 明确 JSON 要求、提供 Schema、few-shot 示例、GBNF 语法约束 |
| Function Calling | 模型原生支持的工具调用能力，返回 `tool_calls` 指令 | 可靠性高，包含意图识别，能与外部世界交互 | 需要模型支持，多轮对话流程较复杂 | OpenAI Function Calling 等 |

## 三、LangChain Output Parsers 比较

| 解析器 | 功能 | 特点 | 适用场景 |
|---|---|---|---|
| `StrOutputParser` | 将 LLM 输出作为字符串返回 | 最基础，不进行结构化解析 | 纯文本输出 |
| `JsonOutputParser` | 解析包含嵌套结构和列表的复杂 JSON 字符串 | 能处理复杂 JSON，但不做严格类型验证 | 需要 JSON 但结构较灵活 |
| `PydanticOutputParser` | 结合 Pydantic 模型，严格定义和验证输出格式 | 生成格式指令，解析并验证为 Pydantic 对象；验证失败抛 `OutputParserException` | 需要严格数据结构与类型验证 |

### PydanticOutputParser 工作步骤

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1. 定义数据模型 | 使用 Pydantic `BaseModel` 定义类，`Field` 的 `description` 作为指令提供给 LLM | 描述需清晰准确 |
| 2. 生成格式指令 | 实例化后调用 `get_format_instructions()`，提取 JSON Schema 并嵌入提示模板 | 明确要求 LLM 输出符合 Schema 的 JSON |
| 3. 构建并执行调用链 | 通过 LCEL 将 `prompt | llm | parser` 链接 | `prompt` 组合用户输入和格式指令，`llm` 生成 JSON 字符串 |
| 4. 解析与验证 | 先解析为 Python 字典，再用 `model_validate()` 验证 | 成功返回 Pydantic 实例，失败抛出异常 |

## 四、LlamaIndex 输出解析比较

| 组件 | 作用 | 说明 |
|---|---|---|
| 响应合成 Response Synthesis | 接收检索到的文本块和查询，智能呈现给 LLM 生成最终答案 | 支持 refine 模式、compact 模式等，默认目标是高质量文本回答 |
| 结构化输出 Structured Output | 需要 LLM 返回结构化数据时使用 Pydantic Programs | 定义 Schema → 引导生成 → 解析验证；若 LLM 支持 Function Calling 则优先使用，否则回退到 JSON Schema 注入提示词 |

> 与 LangChain 的 `PydanticOutputParser` 思想一致：定义 Schema、引导生成、解析验证。

## 五、不依赖框架的简单实现技巧比较

| 技巧 | 做法 | 严格程度 | 适用场景 |
|---|---|---|---|
| 明确要求 JSON 格式 | 在提示中直接强硬要求“必须返回 JSON 对象”“不要包含解释性文字，只返回 JSON” | 一般 | 简单场景，模型能力较强 |
| 提供 JSON Schema | 在提示中给出想要的 JSON 对象模式，描述每个键的含义和数据类型 | 较高 | 需要明确结构 |
| 提供 few-shot 示例 | 给出 1–2 个“用户输入 → 期望 JSON 输出”的完整示例 | 较高 | 让模型学习格式和风格 |
| 使用语法约束 | 对本地部署开源模型使用 GBNF 等语法文件，强制每个 token 符合 JSON 语法 | 最高 | 最严格、最可靠的非 Function Calling 方法 |

## 六、Function Calling 工作流程比较

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1. 定义工具 | 以 JSON Schema 定义可用工具：名称、功能描述、参数 | 描述质量直接影响模型能否正确选择和使用工具 |
| 2. 用户提问 | 用户发起需要调用工具才能回答的请求 | 如“杭州今天天气怎么样？” |
| 3. 模型决策 | 模型分析意图，匹配最合适工具，返回包含 `tool_calls` 的特殊响应 | 不直接回答，而是给出“请调用某某工具，并使用这些参数”的指令 |
| 4. 代码执行 | 应用解析工具名称和参数，在代码层面实际执行工具 | 如调用真实天气 API |
| 5. 结果反馈 | 将工具执行结果包装成 `role` 为 `tool` 的消息，再次发送给模型 | 如 `{"role": "tool", "tool_call_id": ..., "content": "24℃，晴朗"}` |
| 6. 最终生成 | 模型结合原始问题和工具返回信息，生成最终自然语言回答 | 完成多轮对话流程 |

## 七、Function Calling 与传统提示工程比较

| 维度 | 传统提示工程请求 JSON | Function Calling |
|---|---|---|
| 可靠性 | 解析可能格式不稳定的纯文本输出 | 模型原生支持，结构化数据更稳定、精确 |
| 意图识别 | 主要是格式化输出 | 包含“意图到函数的映射”，模型主动选择最合适工具 |
| 与外部世界交互 | 无 | 是构建 AI Agent 的核心基础，可查询数据库、调用 API、控制智能家居等 |
| 流程复杂度 | 单轮或简单多轮 | 多轮对话流程，涉及工具定义、模型决策、代码执行、结果反馈 |
| 适用场景 | 简单结构化输出 | 需要与外部工具协同、执行实际任务的场景 |

## 八、选择建议

| 需求 | 推荐方案 | 理由 |
|---|---|---|
| 快速集成 LangChain 生态 | `PydanticOutputParser` | 严格定义和验证输出格式，开箱即用 |
| 使用 LlamaIndex 构建 RAG | Pydantic Programs | 与响应合成和结构化输出集成，优先使用 Function Calling |
| 不依赖框架、简单场景 | 提示工程 + few-shot 示例 | 灵活，无需额外依赖 |
| 本地部署开源模型、要求严格 JSON | GBNF 语法约束 | 强制每个 token 符合 JSON 语法，最可靠 |
| 需要调用外部工具、执行实际任务 | Function Calling | 可靠性高，包含意图识别，是 Agent 的核心基础 |
| 需要与外部 API 交互 | Function Calling | 模型返回工具调用指令，代码执行后反馈结果，生成最终回答 |

## 九、结论

格式化生成是连接 LLM 自然语言理解与下游程序化逻辑的关键。LangChain 提供 `StrOutputParser`、`JsonOutputParser`、`PydanticOutputParser` 等解析器，其中 `PydanticOutputParser` 通过 JSON Schema 注入和 Pydantic 验证实现最严格的结构化输出。LlamaIndex 将输出解析与生成过程紧密结合，通过响应合成和 Pydantic Programs 支持结构化输出，并优先使用 Function Calling。不依赖框架时，可通过明确 JSON 要求、提供 Schema、few-shot 示例或 GBNF 语法约束实现。Function Calling 是更强大的方案，它不仅是格式化输出，更包含意图到函数的映射，支持与外部世界交互，是构建 AI Agent 的核心基础。实际选择需根据框架依赖、模型能力、输出严格程度和是否需要外部工具交互综合权衡。
