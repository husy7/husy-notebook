# RAG 数据加载与文档加载器比较

> 依据《第二章 数据准备 第一节 数据加载》整理，重点比较文档加载器、Unstructured 元素类型、LangChain 封装与原始 Unstructured、`partition` 与 `partition_pdf`。

## 一、数据加载在 RAG 中的定位

| 维度 | 说明 |
|---|---|
| 环节位置 | RAG 流水线第一步，不可或缺 |
| 输入 | PDF、Word、Markdown、HTML 等非结构化文档 |
| 输出 | 程序可处理的结构化数据：文本 + 元数据 + 统一结构 |
| 核心任务 | 解析原始文档、抽取元数据、整理统一数据结构 |
| 影响 | 直接决定索引构建、检索效果和最终生成质量 |
| 核心原则 | Garbage In, Garbage Out：高质量输入是高质量输出的前提 |

## 二、主流 RAG 文档加载器比较

| 工具名称 | 特点 | 适用场景 | 性能表现 |
|---|---|---|---|
| PyMuPDF4LLM | PDF→Markdown，OCR + 表格识别 | 科研文献、技术手册 | 开源免费，GPU 加速 |
| TextLoader | 基础文本文件加载 | 纯文本处理 | 轻量高效 |
| DirectoryLoader | 批量目录文件处理 | 混合格式文档库 | 支持多格式扩展 |
| Unstructured | 多格式文档解析 | PDF、Word、HTML 等 | 统一接口，智能解析 |
| FireCrawlLoader | 网页内容抓取 | 在线文档、新闻 | 实时内容获取 |
| LlamaParse | 深度 PDF 结构解析 | 法律合同、学术论文 | 解析精度高，商业 API |
| Docling | 模块化企业级解析 | 企业合同、报告 | IBM 生态兼容 |
| Marker | PDF→Markdown，GPU 加速 | 科研文献、书籍 | 专注 PDF 转换 |
| MinerU | 多模态集成解析 | 学术文献、财务报表 | 集成 LayoutLMv3 + YOLOv8 |

## 三、Unstructured 的定位与优势

| 比较维度 | Unstructured |
|---|---|
| 定位 | 面向 RAG 和 AI 微调场景的非结构化数据预处理库 |
| 格式支持 | PDF、Word、Excel、HTML、Markdown 等多种格式 |
| 接口特点 | 统一 API，避免为不同格式分别编写代码 |
| 结构识别 | 自动识别标题、段落、表格、列表等文档结构 |
| 元数据 | 保留相应元数据信息 |
| 适用价值 | 多格式统一解析，是目前应用较广的文档加载方案之一 |

## 四、Unstructured 支持的文档元素类型

| 类别 | 元素类型 | 描述 |
|---|---|---|
| 标题与结构 | Title | 文档标题 |
| 正文 | NarrativeText | 多个完整句子组成的正文文本 |
| 列表 | ListItem | 列表项，属于列表的正文文本元素 |
| 表格 | Table | 表格 |
| 图像 | Image | 图像元数据 |
| 公式 | Formula | 公式 |
| 联系信息 | Address | 物理地址 |
| 联系信息 | EmailAddress | 邮箱地址 |
| 图表说明 | FigureCaption | 图片标题 / 说明文字 |
| 页眉页脚 | Header | 文档页眉 |
| 页眉页脚 | Footer | 文档页脚 |
| 代码 | CodeSnippet | 代码片段 |
| 分页 | PageBreak | 页面分隔符 |
| 分页 | PageNumber | 页码 |
| 其他 | UncategorizedText | 未分类的自由文本 |
| 分块结果 | CompositeElement | 分块处理时产生的复合元素 |

> `CompositeElement` 是由一个或多个连续文本元素组合而成的特殊元素类型，例如多个列表项可能被组合成一个单独的块。

## 五、LangChain 封装 vs 原始 Unstructured

| 维度 | LangChain 封装 | 原始 Unstructured |
|---|---|---|
| 典型用法 | 如 `UnstructuredMarkdownLoader` | 直接使用 `partition` 等函数 |
| 集成速度 | 快，适合快速接入 LangChain 流程 | 需要自行组织解析逻辑 |
| 灵活性 | 相对有限 | 更高 |
| 控制力 | 受封装限制 | 可精细控制参数 |
| 适用场景 | 快速原型、常规加载 | 需要更大灵活性和控制力的场景 |

## 六、`partition` 与 `partition_pdf` 比较

| 维度 | `partition` | `partition_pdf` |
|---|---|---|
| 文件类型 | 自动检测文件类型，并路由到专用函数 | 专用于 PDF |
| 使用方式 | `from unstructured.partition.auto import partition` | `from unstructured.partition.pdf import partition_pdf` |
| 参数特点 | 支持 `filename`、`content_type`、`file`、`url`、`include_page_breaks`、`strategy`、`encoding` 等 | 提供更多 PDF 特有参数，如 OCR 语言设置、图像提取、表格结构推理等 |
| 性能 | 通用解析 | PDF 处理性能更优 |
| 适用场景 | 多格式通用加载 | 需要专业 PDF 处理时 |

> 实际应用中，针对 PDF 的处理，目前更多选用 PaddleOCR、MinerU 等模型或工具。

## 七、选择建议

| 需求 | 建议选择 |
|---|---|
| 纯文本处理 | `TextLoader` |
| 批量目录文件 | `DirectoryLoader` |
| 多格式统一解析 | `Unstructured` |
| 科研文献、技术手册 | `PyMuPDF4LLM`、`Marker` |
| 法律合同、学术论文 | `LlamaParse` |
| 企业合同、报告 | `Docling` |
| 学术文献、财务报表 | `MinerU` |
| 网页内容抓取 | `FireCrawlLoader` |
| 需要深度控制 | 原始 `Unstructured` / `partition_pdf` |
| 快速集成 | LangChain 封装加载器 |

## 八、结论

数据加载质量决定 RAG 系统的上限。选择文档加载器时，应优先明确文档类型、解析精度、元数据需求、性能与成本，再决定使用通用加载器、专用 PDF 工具，还是直接调用原始 Unstructured。对于多格式统一处理，Unstructured 优势明显；对于高精度 PDF 场景，可结合 PyMuPDF4LLM、LlamaParse、Marker、MinerU、PaddleOCR 等工具。
