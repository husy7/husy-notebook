# 文本分块策略与框架比较

> 依据《第二章 数据准备 第二节 文本分块》整理，重点比较分块的重要性、基础策略、语义断点方法、开源框架方案与选择建议。

## 一、文本分块在 RAG 中的定位

| 维度 | 说明 |
|---|---|
| 定义 | 将加载后的长篇文档切分成更小、更易于处理的单元 |
| 输出 | 文本块，是后续向量检索和模型处理的基本单位 |
| 位置 | 数据准备阶段的关键步骤 |
| 目标 | 在模型限制内，尽可能保留语义完整性与主题聚焦性 |
| 影响 | 直接决定向量质量、检索精度和生成答案质量 |

## 二、为什么必须分块

### 2.1 满足模型上下文限制

| 组件 | 限制 | 对分块的要求 |
|---|---|---|
| 嵌入模型 | 有严格输入长度上限，如 bge-base-zh-v1.5 为 512 token | 文本块必须小于等于嵌入模型上下文窗口，否则被截断、信息丢失 |
| 大语言模型 | 上下文窗口有限，从几千到上百万 token 不等 | 检索到的所有文本块、用户问题和提示词都必须能放入窗口 |
| 总体要求 | 分块是文本被两个模型完整、有效处理的基础 | 块过大或过小都会影响系统效果 |

### 2.2 为何“块”不是越大越好

| 问题 | 原因 | 后果 | 对策 |
|---|---|---|---|
| 嵌入过程中的信息损失 | 嵌入模型通过池化将整个文本块压缩成单一向量，块越长，语义越稀释 | 向量表示笼统，关键细节模糊，检索精度下降 | 控制块大小，避免一个块承载过多语义点 |
| 生成过程中的“大海捞针” | LLM 处理长上下文时，倾向记住开头和结尾，忽略中间 | 关键信息被淹没在无关内容中，回答质量下降或产生幻觉 | 提供聚焦、少噪音的上下文块 |
| 主题稀释导致检索失败 | 一个块包含多个不相关主题，整体语义被稀释 | 与查询相关的块也可能因相关性得分低而无法被召回 | 按主题切分，让每个块聚焦单一主题 |

## 三、基础分块策略比较

| 策略 | 核心原理 | 关键实现/参数 | 优点 | 缺点/局限 | 适用场景 |
|---|---|---|---|---|---|
| 固定大小分块 | 按字符数或分隔符切分，并合并为接近 `chunk_size` 的块 | `CharacterTextSplitter`，默认分隔符 `"\n\n"`，`chunk_size`、`chunk_overlap` | 实现简单、速度快、计算开销小 | 可能在语义边界切断；LangChain 实现更准确说是“段落感知的自适应分块” | 日志分析、数据预处理、对语义连续性要求不高的场景 |
| 递归字符分块 | 使用有层次结构的分隔符递归切分，超长片段继续用更细粒度分隔符处理 | `RecursiveCharacterTextSplitter`，分隔符优先级如 `["\n\n", "\n", "。", "，", " ", ""]`；支持多语言和编程语言特化 | 平衡语义完整性与块大小控制；比固定大小分块更能处理超长文本 | 仍依赖预设分隔符；对语义主题变化不敏感 | 通用长文本、多语言文本、代码文档 |
| 语义分块 | 根据句子间语义差异识别断点，在主题显著变化处切分 | `SemanticChunker`；句子分割、上下文感知嵌入、余弦距离、断点识别、合并 | 每个块内部语义一致性高，主题聚焦 | 需要嵌入模型，计算成本更高；阈值选择影响效果 | 语义要求高、主题边界模糊的长文本 |
| 基于文档结构的分块 | 利用 Markdown、HTML、LaTex 等结构标记，按标题层级切分 | `MarkdownHeaderTextSplitter`；标题映射、内容聚合、元数据注入 | 保留宏观逻辑结构，元数据提供精确“地址” | 单章节可能过长；通常需与递归分块组合 | 结构清晰的 Markdown、HTML、LaTex 文档 |

### 关键补充

| 策略 | 补充说明 |
|---|---|
| 固定大小分块 | 优先保持段落完整性；单个段落超过 `chunk_size` 时发出警告但仍保留为完整块；通过 `chunk_overlap` 保持上下文连续性 |
| 递归字符分块 | 从高优先级分隔符开始，若片段仍超长则递归使用下一级分隔符，直到满足大小要求；分隔符用尽时保留超长块 |
| 语义分块 | 不是对每个句子独立嵌入，而是通过 `buffer_size` 捕捉上下文；断点阈值方法包括百分位、标准差、四分位距、梯度 |
| 基于文档结构的分块 | 推荐两阶段：先用 `MarkdownHeaderTextSplitter` 按标题切分并注入元数据，再用 `RecursiveCharacterTextSplitter` 细分 |

## 四、语义分块断点识别方法比较

| 方法 | 逻辑 | 默认参数 | 特点/适用 |
|---|---|---|---|
| `percentile` | 计算所有相邻句子语义差异值，超过某个百分位阈值即为断点 | `breakpoint_threshold_amount=95` | 默认方法；只选最显著的 5% 语义差异点 |
| `standard_deviation` | 差异值超过“平均值 + N × 标准差”视为断点 | `breakpoint_threshold_amount=3` | 基于统计异常值识别语义跳跃 |
| `interquartile` | 差异值超过 `Q3 + N × IQR` 视为断点 | `breakpoint_threshold_amount=1.5` | 使用四分位距识别异常值 |
| `gradient` | 先计算差异值变化率，再对梯度应用百分位法 | `breakpoint_threshold_amount=95` | 适合语义联系紧密、差异值普遍较低的文本，如法律、医疗文档 |

## 五、开源框架分块策略比较

| 框架 | 核心思路 | 分块方法/特点 | 优势 | 局限/注意 |
|---|---|---|---|---|
| Unstructured | 先分区再分块，基于文档元素进行智能组合 | `basic`：连续组合元素直到 `max_characters`；`by_title`：将 `Title` 视为新章节开始，强制新块 | 先理解、后分割，保留原始语义结构；适合版式复杂文档 | 依赖分区质量；分块策略相对固定 |
| LlamaIndex | 面向“节点”的解析与转换，分块是节点转换的一环 | 结构感知型、语义感知型、常规型；`SentenceWindowNodeParser` 存储前后 N 句窗口；支持转换流水线 | 节点解析器丰富，元数据完整；可与 LangChain 互操作 | 体系相对复杂，需要理解节点与转换流水线 |
| ChunkViz | 可视化分块工具 | 输入文档和分块配置，用不同颜色展示 chunk 边界和重叠 | 直观理解分块逻辑，便于调参 | 主要用于可视化，不直接参与生产流程 |

### LlamaIndex 节点解析器分类

| 类型 | 代表 | 特点 |
|---|---|---|
| 结构感知型 | `MarkdownNodeParser`、`JSONNodeParser`、`CodeSplitter` | 根据源文件结构切分 |
| 语义感知型 | `SemanticSplitterNodeParser`、`SentenceWindowNodeParser` | 用嵌入检测语义断点；句子窗口保留上下文 |
| 常规型 | `TokenTextSplitter`、`SentenceSplitter` | 基于 token 数量或句子边界切分 |

## 六、组合策略与选择建议

| 场景 | 推荐策略 | 理由 |
|---|---|---|
| 通用长文本 | 递归字符分块 | 平衡语义完整性与块大小控制 |
| 语义要求高 | 语义分块 | 在主题显著变化处切分，块内一致性高 |
| Markdown/HTML/LaTex | 结构分块 + 递归分块 | 保留标题层级和元数据，同时控制块大小 |
| 版式复杂 PDF | Unstructured `by_title` | 基于文档元素和章节感知分块 |
| 需要句子级上下文 | LlamaIndex `SentenceWindowNodeParser` | 精确匹配句子，同时向 LLM 提供上下文窗口 |
| 代码文档 | 递归字符分块 + 语言特化 | 使用符合代码结构的分隔符 |
| 可视化调参 | ChunkViz | 直观查看块边界和重叠 |

## 七、结论

文本分块是 RAG 数据准备中的关键环节。分块不是越大越好，块过大导致嵌入信息损失、Lost in the Middle、主题稀释和检索失败；块过小则可能丢失上下文。没有万能策略，应根据文档结构、模型上下文窗口、检索精度要求和计算成本选择。实践中，推荐采用组合策略：先用结构分块保留宏观逻辑与元数据，再用递归或语义分块控制粒度。核心目标始终是：在模型限制内，让每个块主题聚焦、语义完整、上下文连续，从而提升检索信噪比和最终生成质量。
