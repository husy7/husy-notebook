# 查询构建：文本到元数据过滤器与文本到Cypher比较

> 依据《第四章 检索优化 第二节 查询构建》整理，重点比较查询构建的定位、Self-Query Retriever 工作流程、文本到元数据过滤器与文本到Cypher、代码实践与输出结果，并分析思考题。

## 一、查询构建在 RAG 中的定位

| 维度 | 说明 |
|---|---|
| 解决的问题 | 用户查询不仅是语义匹配，还可能包含复杂过滤、聚合或关系查询 |
| 数据类型 | 结构化数据（SQL）、半结构化数据（带元数据文档）、图数据 |
| 核心方法 | 利用 LLM 将自然语言查询“翻译”成针对特定数据源的结构化查询语言或带过滤条件的请求 |
| 目标 | 让 RAG 系统无缝连接和利用各种类型的数据，扩展应用场景 |
| 在流程中的位置 | 高级 RAG 流程中的关键环节，位于检索优化阶段 |

## 二、文本到元数据过滤器 vs 文本到Cypher

| 比较维度 | 文本到元数据过滤器 | 文本到Cypher |
|---|---|---|
| 适用数据源 | 向量数据库中的文档块元数据 | 图数据库（如 Neo4j） |
| 核心组件 | LangChain 的 `SelfQueryRetriever` | LangChain 的 `GraphCypherQAChain` 等工具链 |
| 查询语言 | 通用结构化查询对象，再翻译为向量数据库原生过滤语法 | Cypher 查询语言 |
| 工作方式 | 将自然语言分解为查询字符串 + 元数据过滤器 | 将自然语言根据图谱 Schema 翻译为 Cypher 查询 |
| 执行过程 | 语义搜索 + 元数据过滤的复合查询 | 在图数据库上执行 Cypher，获取结构化数据 |
| 输出 | 返回最相关的文档块 | 返回精确的结构化数据，可选再由 LLM 生成自然语言答案 |
| 关键依赖 | 清晰的元数据字段描述（`AttributeInfo`） | 预先提供的图谱模式（Schema） |
| 典型场景 | 视频元数据检索，如“2022年发布的机器学习论文” | 图数据关系查询，如“Tomaz 住在哪个国家” |
| 对 LLM 要求 | 需要准确解析过滤条件，`temperature=0` 保证稳定 | 通常需要性能较强的 LLM 确保转换准确性 |

## 三、Self-Query Retriever 工作流程

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1. 定义元数据结构 | 向 LLM 描述文档内容和每个元数据字段的含义及类型 | 使用 `AttributeInfo` 定义名称、类型、自然语言描述 |
| 2. 查询解析 | 调用 LLM 将自然语言查询分解为两部分 | 查询字符串（用于语义搜索）+ 元数据过滤器（结构化过滤条件） |
| 3. 执行查询 | 将查询字符串和元数据过滤器发送给向量数据库 | 执行同时包含语义搜索和元数据过滤的复合查询 |
| 示例 | “关于2022年发布的机器学习的论文” | 解析为查询字符串“机器学习的论文”，过滤器 `year == 2022` |

## 四、代码实践关键组件比较

| 组件 | 作用 | 关键代码/参数 |
|---|---|---|
| 数据加载 | 加载 B 站视频文档和元数据 | `BiliBiliLoader`；手动提取扁平化 `metadata` |
| 向量存储 | 存储文档和嵌入 | `Chroma.from_documents(bili, embed_model)` |
| 元数据字段配置 | 告诉 LLM 每个字段的含义和类型 | `AttributeInfo(name, description, type)` |
| 创建自查询检索器 | 构建查询构造链和数据库翻译器 | `SelfQueryRetriever.from_llm(llm, vectorstore, document_contents, metadata_field_info, enable_limit=True, verbose=True)` |
| LLM 配置 | 控制输出随机性 | `ChatDeepSeek(model="deepseek-chat", temperature=0, api_key=...)` |
| 执行查询 | 用自然语言调用检索器 | `retriever.invoke(query)` |

## 五、查询输出结果比较

| 查询 | 生成的内部查询 | 返回结果 | 问题/说明 |
|---|---|---|---|
| “时间最短的视频” | `query=' ' filter=None limit=1` | 返回《吴恩达 x OpenAI Prompt课程》02，时长 1063 秒 | 未正确解析“最短”为排序条件，只设置了 `limit=1`，结果并非真正最短 |
| “时长大于600秒的视频” | `query=' ' filter=Comparison(comparator=GT, attribute='length', value=600) limit=None` | 返回时长 806 秒和 1063 秒的两个视频 | 过滤条件正确，但未排序；结果符合“大于600秒” |

## 六、思考题分析：为什么“时间最短的视频”结果错误？

| 可能原因 | 说明 |
|---|---|
| 排序意图未被解析 | 自查询检索器将“最短”理解为 `limit=1`，但没有生成按 `length` 升序排序的条件 |
| 元数据字段描述不足 | `length` 描述为“视频长度，以秒为单位的整数”，但未明确支持排序操作 |
| LLM 查询构造能力限制 | 查询构造器可能只支持过滤和限制，不直接支持排序；或提示不够明确 |
| 向量数据库翻译器限制 | Chroma 的翻译器可能不支持排序，只支持过滤和 `limit` |
| 结果表现 | 返回的是第一个匹配项，而非全局最短，说明排序逻辑缺失 |

## 七、选择建议

| 需求 | 推荐方案 | 理由 |
|---|---|---|
| 向量数据库 + 元数据过滤 | 文本到元数据过滤器（Self-Query Retriever） | 将自然语言分解为语义查询和结构化过滤，适合文档元数据筛选 |
| 图数据库 + 关系查询 | 文本到Cypher | 直接翻译为 Cypher，利用图数据库的关系查询能力 |
| 需要排序、聚合等复杂操作 | 谨慎评估自查询检索器能力，必要时自定义查询构造 | 示例显示“最短”排序未被正确处理 |
| 需要稳定、可复现的查询转换 | 设置 `temperature=0` | 确保相同输入生成相同结构化查询 |
| 生产环境 | 确保元数据描述准确、无歧义，并测试边界查询 | 减少解析错误 |

## 八、结论

查询构建是 RAG 系统连接非结构化与结构化数据的关键技术。文本到元数据过滤器通过 `Self-Query Retriever` 将自然语言拆解为语义查询和元数据过滤，适合向量数据库中的文档元数据筛选；文本到Cypher 则面向图数据库，将自然语言翻译为 Cypher 查询，适合关系型结构化数据。两者都依赖 LLM 的理解能力，但前者需要清晰的元数据字段描述，后者需要准确的图谱 Schema。代码示例显示，自查询检索器能正确处理“时长大于600秒”这类过滤，但对“时间最短”这类排序需求解析失败，只生成了 `limit=1` 而未排序，导致结果错误。因此，在实际应用中，需要根据查询复杂度评估工具能力，必要时自定义查询构造逻辑，并保持 `temperature=0` 以确保转换稳定。
