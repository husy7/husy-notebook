# 混合检索：稀疏向量与密集向量比较

> 依据《第四章 检索优化 第一节 混合检索》整理，重点比较稀疏向量与密集向量、RRF 与加权线性组合、单一检索与混合检索、Milvus 实践流程与结果。

## 一、混合检索要解决的核心问题

| 检索方式 | 优势 | 局限 |
|---|---|---|
| 稀疏向量检索 | 关键词精确匹配，专业术语、特定名词、产品型号等检索效果好，可解释性强 | 无法理解语义，存在“词汇鸿沟”，难以识别同义词 |
| 密集向量检索 | 理解同义词、近义词和上下文关系，泛化能力强，语义搜索表现好 | 可解释性差，依赖大量数据和算力，可能忽略必须精确匹配的关键词 |
| 混合检索 | 同时利用稀疏向量的精确性和密集向量的泛化性 | 计算资源消耗大，参数调试复杂，融合后可解释性仍是挑战 |

## 二、稀疏向量 vs 密集向量

| 维度 | 稀疏向量 | 密集向量 |
|---|---|---|
| 别称 | 词法向量 | 语义向量 |
| 基础 | 词频统计、传统信息检索 | 深度学习模型学习到的表示 |
| 维度 | 极高，通常与词汇表大小相当 | 低维、稠密，如 768、1024 维 |
| 元素特点 | 绝大多数为零，只存非零值 | 所有维度都有值 |
| 表示方式 | 字典/键值对、坐标列表 COO | 数组 `[]` |
| 权重/算法 | TF-IDF、BM25 | Word2Vec、GloVe、BERT、GPT 等嵌入 |
| 核心能力 | 关键词精确匹配 | 语义理解、同义词、上下文关系 |
| 可解释性 | 强，每个维度对应一个词 | 弱，每个维度通常没有具体物理意义 |
| OOV 处理 | 对未登录词会完全忽略 | 通过子词分割如 BPE、WordPiece 更好处理 OOV |
| 主要缺点 | 无法识别“汽车”和“轿车”是同义词 | 可能忽略必须精确匹配的关键词 |

### 实例对比

| 类型 | 示例 | 说明 |
|---|---|---|
| 稀疏向量 | `{ "88": 1.2, "666": 0.8, "999": 1.5 }` | “西红柿”“炒”“蛋”对应不同索引，无法理解“番茄”与“西红柿”的语义相似性 |
| 密集向量 | `[0.89, -0.12, 0.77, ..., -0.45]` | 可能在语义空间中接近“番茄鸡蛋面”“洋葱炒鸡蛋”等菜肴向量 |
| 查询示例 | “蛋白质丰富的家常菜” | 即使查询中没有原文关键词，密集向量也可能成功匹配菜谱 |

## 三、混合检索融合方法比较

| 融合方法 | 核心思想 | 公式/参数 | 特点 | 适用 |
|---|---|---|---|---|
| RRF 倒数排序融合 | 不关心原始得分，只关心文档在各自结果集中的排名 | `RRFscore(d)=Σ 1/(rank_i(d)+c)`，`c` 通常为 60 | 排名越靠前最终得分越高；对异构得分不敏感，融合稳健 | 多路检索结果得分不可比时 |
| 加权线性组合 | 先归一化各检索得分，再按权重线性组合 | `Hybridscore=α·Densescore+(1−α)·Sparsescore` | 可灵活控制语义与关键词贡献比例 | 需要按业务调整关键词与语义权重时 |

## 四、混合检索优势与局限

| 优势 | 说明 |
|---|---|
| 召回率与准确率高 | 同时捕获关键词和语义，显著优于单一检索 |
| 灵活性强 | 可通过融合策略和权重调整适应不同业务场景 |
| 容错性好 | 关键词检索可部分弥补向量模型对拼写错误或罕见词的敏感性 |

| 局限 | 说明 |
|---|---|
| 计算资源消耗大 | 需要同时维护和查询两套索引 |
| 参数调试复杂 | 融合权重等超参数需要反复实验调优 |
| 可解释性仍是挑战 | 融合后的结果排序理由难以直观分析 |

## 五、Milvus 混合检索实践步骤比较

| 步骤 | 操作 | 关键点 |
|---|---|---|
| 步骤一：定义 Collection | 定义 Schema，包含标量字段、稀疏向量字段、密集向量字段 | 稀疏向量 `SPARSE_FLOAT_VECTOR`；密集向量 `FLOAT_VECTOR`，如 1024 维 |
| 步骤二：BGE-M3 双向量生成 | 使用 BGE-M3 同时生成稀疏向量和密集向量 | `embeddings["sparse"]`、`embeddings["dense"]` |
| 步骤三：创建索引 | 稀疏向量用 `SPARSE_INVERTED_INDEX`；密集向量用 `AUTOINDEX` | 度量类型均为 `IP` |
| 步骤四：插入数据 | 按 Schema 字段顺序批量插入 | 包含 7 个标量字段 + 2 个向量字段；`flush()` 使数据立即可搜索 |
| 步骤五：执行混合检索 | 分别构造稀疏和密集 `AnnSearchRequest`，用 `RRFRanker` 融合 | `RRFRanker(k=60)`；`collection.hybrid_search` |

## 六、单独检索 vs 混合检索结果比较

示例查询：`悬崖上的巨龙`  
过滤器：`category in ["western_dragon", "chinese_dragon", "movie_character"]`

| 排名 | 单独密集向量检索 | 单独稀疏向量检索 | 混合检索 |
|---|---|---|---|
| 1 | 悬崖上的白龙，Score 0.7219 | 悬崖上的白龙，Score 0.2319 | 悬崖上的白龙，Score 0.0328 |
| 2 | 中华金龙，Score 0.5131 | 中华金龙，Score 0.0923 | 中华金龙，Score 0.0320 |
| 3 | 驯龙高手：无牙仔，Score 0.5119 | 驯龙高手：无牙仔，Score 0.0691 | 霸王龙的怒吼，Score 0.0318 |
| 4 | — | — | 奔跑的奶龙，Score 0.0313 |
| 5 | — | — | 驯龙高手：无牙仔，Score 0.0310 |

> 单独检索输出只展示了前 3 条；实际 `limit=top_k=5`，但文本中未完整列出全部结果。混合检索中出现了霸王龙和奶龙，并将驯龙高手挤到第 5。

## 七、为什么驯龙高手在混合检索中降到第五？

| 原因 | 说明 |
|---|---|
| 混合检索未应用过滤器 | 代码中单独搜索使用了 `expr=search_filter`，但创建 `AnnSearchRequest` 时没有传入 `expr`，导致混合检索候选集不同 |
| RRF 只看排名，不看原始得分 | 霸王龙、奶龙可能在某一路或两路中排名靠前，融合后综合排名上升 |
| 两路排名综合效应 | 驯龙高手虽在单独检索中均排第 3，但混合检索中其他文档在两路中的排名组合更优 |
| 候选集扩大 | 未过滤时更多文档参与检索，可能引入原本被过滤掉的候选，改变最终排序 |

## 八、选择建议

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| 专业术语、产品型号、函数名检索 | 稀疏向量或混合检索 | 关键词精确匹配不可替代 |
| 语义问答、同义词、上下文理解 | 密集向量或混合检索 | 语义泛化能力强 |
| 复杂搜索场景 | 混合检索 | 同时利用关键词和语义优势 |
| 得分不可比的多路结果 | RRF | 不依赖原始得分，只依赖排名，融合稳健 |
| 需要按业务调整权重 | 加权线性组合 | 可通过 α 控制语义与关键词贡献 |
| 生产环境 | 混合检索 + 过滤条件 | 注意过滤条件需同时应用于各路检索请求 |

## 九、结论

混合检索通过结合稀疏向量和密集向量，弥补了单一检索的局限：稀疏向量擅长关键词精确匹配，密集向量擅长语义理解。融合策略中，RRF 关注排名，适合异构结果融合；加权线性组合关注得分，适合按业务调整权重。Milvus 通过 `SPARSE_INVERTED_INDEX`、`AUTOINDEX` 和 `RRFRanker` 支持完整的混合检索流程。示例中，单独检索和混合检索结果存在差异，驯龙高手从第 3 降到第 5，关键原因之一是混合检索的 `AnnSearchRequest` 未传入 `expr` 过滤器，导致候选集不同，同时 RRF 只依据排名融合，使其他文档综合排名上升。实践中，必须保证过滤条件在单独检索和混合检索中一致，并根据业务需求选择融合方法和参数。
