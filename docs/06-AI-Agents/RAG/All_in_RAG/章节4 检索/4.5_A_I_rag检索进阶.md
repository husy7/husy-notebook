# 检索进阶技术：重排序、压缩与校正比较

> 依据《第四章 检索优化 第五节 检索进阶》整理，重点比较重排序方法、压缩策略、校正流程，以及三者之间的关系与选择建议。

## 一、检索进阶技术概览

| 技术 | 目标 | 解决的核心问题 |
|---|---|---|
| 重排序 Re-ranking | 对初步检索结果重新排序，提升相关性 | 最相关文档不总在顶端，语义理解有偏差 |
| 压缩 Compression | 从检索结果中提炼、过滤，只保留最相关信息 | 上下文冗长、噪音多，增加成本并降低生成质量 |
| 校正 Correcting | 评估检索文档质量，决定是否修正或寻求外部知识 | 检索可能失败，返回不相关、过时或错误文档，导致幻觉 |

## 二、重排序方法比较

| 特性 | RRF | RankLLM | Cross-Encoder | ColBERT |
|---|---|---|---|---|
| 核心机制 | 融合多个排名 | LLM 推理，生成排序列表 | 联合编码查询与文档，计算单一相关分 | 独立编码，后期交互 |
| 计算成本 | 低（简单数学计算） | 中（API 费用与延迟） | 高（N 次模型推理） | 中（向量点积计算） |
| 交互粒度 | 无（仅排名） | 概念/语义级 | 句子级（Query-Doc Pair） | Token 级 |
| 是否依赖模型训练 | 零样本，不依赖训练 | 依赖 LLM | 依赖预训练 Transformer | 依赖预训练模型 |
| 优点 | 简单、稳健，融合多路召回 | 灵活，能理解复杂语义 | 精度高 | 平衡精度与效率，捕捉细粒度交互 |
| 缺点 | 忽略原始相似度分数 | 成本较高，依赖 LLM 稳定性 | 延迟高，N 次独立推理 | 实现较复杂，需后期交互计算 |
| 适用场景 | 多路召回结果融合 | 高价值语义理解场景 | Top-K 精排 | Top-K 重排 |
| 常见模型/实现 | Milvus `RRFRanker` | LLM 提示词排序 | `ms-marco-MiniLM-L-12-v2`、`ms-marco-TinyBERT-L-2-v2` | ColBERT 类模型，可自定义 `ColBERTReranker` |

## 三、压缩方法比较

| 方法 | 类型 | 核心机制 | 优点 | 缺点 | 所属框架 |
|---|---|---|---|---|---|
| `LLMChainExtractor` | 内容提取 | 遍历每个文档，用 LLM Chain 提取与查询相关部分 | 精准提取相关句子，减少噪音 | 增加 LLM 调用成本与延迟 | LangChain |
| `LLMChainFilter` | 文档过滤 | 用 LLM 判断整个文档是否相关，相关则保留，否则丢弃 | 过滤不相关文档，保留完整上下文 | 同样依赖 LLM，成本较高 | LangChain |
| `EmbeddingsFilter` | 文档过滤 | 计算查询与文档嵌入相似度，保留超过阈值的文档 | 快速、成本低 | 精度依赖嵌入质量，可能漏掉相关文档 | LangChain |
| `ColBERTReranker` + `DocumentCompressorPipeline` | 自定义重排 + 压缩管道 | 继承 `BaseDocumentCompressor`，实现 `compress_documents`；用 ColBERT 后期交互计算分数并排序，再组合其他压缩器 | 灵活集成未官方支持的功能，可组合“重排 + 压缩” | 实现较复杂，需理解源码与基类 | LangChain 自定义 |
| `SentenceEmbeddingOptimizer` | 内容提取 | 将文档分解为句子，计算每个句子与查询的嵌入相似度，只保留最相似句子 | 去除无关信息，优化文档 | 可能丢失句子间上下文 | LlamaIndex |

### 压缩管道示例流程

| 步骤 | 操作 | 说明 |
|---|---|---|
| 1 | 基础检索 | `base_retriever` 从向量库初步召回 Top-20 文档 |
| 2 | ColBERT 重排 | 自定义 `ColBERTReranker` 对文档进行 Token 级后期交互重排 |
| 3 | LLM 压缩 | `LLMChainExtractor` 从重排后的文档中提取与查询相关的句子 |
| 4 | 最终返回 | `ContextualCompressionRetriever` 输出压缩后的结果 |

## 四、校正检索（C-RAG）流程比较

| 阶段 | 操作 | 评估结果 | 后续行动 |
|---|---|---|---|
| 检索 Retrieve | 根据用户查询从知识库检索一组文档 | — | — |
| 评估 Assess | 检索评估器判断每个文档与查询的相关性 | 正确 Correct | 进入知识精炼：将文档分解为更小知识片段，过滤无关部分，重新组合成精准上下文 |
| 评估 Assess | 检索评估器判断每个文档与查询的相关性 | 不正确 Incorrect | 触发知识搜索：先查询重写，生成更适合搜索引擎的查询，再进行 Web 搜索 |
| 评估 Assess | 检索评估器判断每个文档与查询的相关性 | 模糊 Ambiguous | 触发知识搜索：通常直接使用原始查询进行 Web 搜索，获取额外信息辅助生成 |
| 行动 Act | 根据评估结果执行不同流程 | — | 增强鲁棒性，减少幻觉，提升答案准确性和可靠性 |

### 校正检索与传统 RAG 比较

| 维度 | 传统 RAG | C-RAG |
|---|---|---|
| 对检索结果的假设 | 检索到的文档总是相关且包含正确答案 | 不盲目信任检索结果 |
| 是否有评估层 | 无 | 有检索评估器，给出正确/不正确/模糊标签 |
| 失败处理 | 直接将“有毒”上下文喂给 LLM，可能导致幻觉 | 根据评估结果进行知识精炼或 Web 搜索 |
| 鲁棒性 | 较低 | 较高，增加“事实核查”层 |
| 实现工具 | 基础检索器 + 生成器 | LangGraph 等图结构，支持条件判断和循环 |

## 五、重排序、压缩、校正的关系比较

| 技术 | 在流程中的位置 | 主要作用 | 与其他技术的关系 |
|---|---|---|---|
| 重排序 | 初步检索之后，生成之前 | 重新排列文档顺序，提升 Top-K 相关性 | 可为压缩提供更优质的输入；ColBERT 等也可用于压缩管道中 |
| 压缩 | 重排序之后，生成之前 | 提炼、过滤文档内容，减少噪音和成本 | 可组合多个压缩器形成管道；也可与重排序串联 |
| 校正 | 检索之后，生成之前 | 评估检索质量，决定是否修正或外部搜索 | 可包含查询重写、知识精炼、Web 搜索等，是更高层的自我修正循环 |

## 六、选择建议

| 需求 | 推荐方案 | 理由 |
|---|---|---|
| 多路召回结果融合 | RRF | 简单、稳健，只依赖排名，不依赖原始分数 |
| 高价值语义理解场景 | RankLLM | LLM 直接判断相关性，灵活但成本较高 |
| Top-K 精排，追求高精度 | Cross-Encoder | 联合编码查询与文档，精度高，但延迟高 |
| 平衡精度与效率 | ColBERT | 独立编码 + 后期交互，Token 级细粒度，成本适中 |
| 减少上下文噪音与成本 | 压缩（`LLMChainExtractor`、`EmbeddingsFilter` 等） | 只保留相关信息，降低 API 成本和延迟 |
| 需要自定义重排逻辑 | 继承 `BaseDocumentCompressor` | 可集成未官方支持的功能，如 ColBERTReranker |
| 检索可能失败，需要自我修正 | C-RAG | 引入评估器，根据正确/不正确/模糊采取不同行动 |
| 生产级高鲁棒性 RAG | 重排序 + 压缩 + 校正组合 | 层层优化，提升相关性、降低成本、减少幻觉 |

## 七、结论

检索进阶技术是构建生产级 RAG 应用的关键。重排序通过 RRF、RankLLM、Cross-Encoder、ColBERT 等方法，解决“最相关文档不总在顶端”的问题，其中 RRF 成本最低，Cross-Encoder 精度最高，ColBERT 在精度与效率之间取得平衡。压缩通过内容提取和文档过滤，减少上下文噪音与 API 成本，LangChain 提供 `ContextualCompressionRetriever` 和多种 `DocumentCompressor`，并支持自定义管道；LlamaIndex 提供 `SentenceEmbeddingOptimizer`。校正通过 C-RAG 引入“检索-评估-行动”循环，在检索失败时进行知识精炼或 Web 搜索，显著增强鲁棒性。三者不是孤立的，而是可以组合使用：先重排序提升排序质量，再压缩提炼内容，最后用校正机制评估并修正。实际选择需根据业务对精度、延迟、成本、鲁棒性的要求综合权衡。
