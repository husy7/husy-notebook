# 查询重构与分发：查询翻译与查询路由比较

> 依据《第四章 检索优化 第四节 查询重构与分发》整理，重点比较查询翻译四种技术、查询路由应用场景、两种路由实现方法，以及 LangChain 与 LlamaIndex 的路由差异。

## 一、查询重构与分发的定位

| 维度 | 说明 |
|---|---|
| 解决的问题 | 用户原始问题往往不是最优检索输入，可能过于复杂、有歧义，或与文档措辞存在偏差 |
| 发生阶段 | 检索之前，对用户查询进行“预处理” |
| 两个关键技术 | 查询翻译、查询路由 |
| 查询翻译目标 | 将原始问题转换成一个或多个更适合检索的形式 |
| 查询路由目标 | 根据问题性质，智能分发到最合适的数据源或检索器 |
| 核心价值 | 弥合用户自然语言提问与文档库存储信息之间的“语义鸿沟” |

## 二、查询翻译四种技术比较

| 技术 | 核心思想 | 做法 | 优点 | 局限/注意 | 适用场景 |
|---|---|---|---|---|---|
| 提示工程 | 通过精心设计的 Prompt 引导 LLM 改写查询或生成可执行指令 | 要求 LLM 输出结构化 JSON 指令，如排序字段和方向；代码解析后执行排序 | 灵活，可处理“时间最短的视频”等最值查询；将 LLM 从文本改写员提升为智能代理 | 依赖 LLM 输出格式，需要解析与校验；示例中 `temperature=0`、`response_format={"type":"json_object"}` | SelfQueryRetriever 无法处理的排序、比较、最值查询 |
| 多查询分解 Multi-query | 将复杂问题拆成多个更简单、更具体的子问题 | LLM 从不同角度分解原始问题，并行检索，合并去重 | 丰富检索结果，覆盖多个子主题，提升后续生成质量 | 增加检索次数和 LLM 调用成本；可能引入冗余 | 复杂问题、多主题、多意图查询 |
| 退步提示 Step-Back Prompting | 引导模型“退后一步”，先抽象出更高层次的通用问题 | 先由原始具体问题生成退步问题，获取通用原理，再结合原问题推理 | 帮助构建更坚实的逻辑基础，提高复杂问答准确性 | 需要两步处理，增加延迟与调用成本 | 细节繁多、过于具体、需要原理支撑的问题 |
| HyDE 假设性文档嵌入 | 先生成“假设性理想答案文档”，再用其向量检索真实文档 | 生成假设文档 → 编码为向量 → 在向量数据库中相似性搜索 | 无需微调即可显著提升向量检索质量；把“查询到文档”匹配转为“文档到文档”匹配 | 假设文档不必完全符合事实；生成质量影响效果 | 查询简短、关键词有限、与文档存在语义鸿沟的向量检索 |

### 2.1 提示工程解决 SelfQueryRetriever 排序问题的比较

| 对比项 | SelfQueryRetriever | 提示工程 + LLM 生成指令 |
|---|---|---|
| 对“时间最短的视频”的处理 | 只生成 `limit=1`，未排序，结果错误 | LLM 输出 `{"sort_by": "length", "order": "asc"}`，代码执行排序 |
| 能力定位 | 将自然语言分解为查询字符串和元数据过滤器 | 理解复杂意图，生成可执行计划 |
| 灵活性 | 受框架和向量数据库翻译器限制 | 高，可按需定义 JSON 指令结构 |
| 稳定性 | 依赖框架内部逻辑 | 设置 `temperature=0`，指定 JSON 格式，确保稳定 |
| 适用场景 | 常规元数据过滤 | 排序、比较、最值等复杂查询 |

## 三、查询翻译技术选择建议

| 需求 | 推荐技术 | 理由 |
|---|---|---|
| 排序、比较、最值查询 | 提示工程生成结构化指令 | 直接让 LLM 输出排序字段和方向，代码执行 |
| 复杂多主题问题 | 多查询分解 | 拆成子问题并行检索，合并去重 |
| 需要通用原理支撑的具体问题 | 退步提示 | 先抽象再推理，提高准确性 |
| 查询简短、关键词少、向量检索效果差 | HyDE | 生成假设文档，提升向量匹配质量 |
| 成本敏感、延迟敏感 | 谨慎使用多查询分解和退步提示 | 这些技术会增加 LLM 调用和检索次数 |

## 四、查询路由的定位与应用场景

查询路由是复杂 RAG 系统中的“智能调度中心”，本质是替代硬编码规则，通过语义理解将查询分发至最匹配的数据源、处理组件或提示模板。

| 应用场景 | 说明 | 示例 |
|---|---|---|
| 数据源路由 | 根据查询意图路由到不同知识库 | “最新 iPhone 有什么功能？”→ 产品文档向量数据库；“我上次订购了什么？”→ 用户历史 SQL 数据库；“A 公司和 B 公司的投资关系？”→ 企业知识图谱数据库 |
| 组件路由 | 根据问题复杂性分配给不同处理组件，平衡成本和效果 | 简单 FAQ → 向量检索；复杂操作或外部 API → 调用 Agent |
| 提示模板路由 | 为不同任务动态选择最优提示词模板 | 数学问题 → 分步思考模板；代码生成 → 代码优化模板 |

## 五、查询路由两种实现方法比较

| 方法 | 核心 | 实现流程 | 优点 | 缺点 | 代表 |
|---|---|---|---|---|---|
| 基于 LLM 的意图识别 | 用 LLM 对查询进行分类，输出路由标签 | 定义路由选项 → LLM 分析并输出决策标签 → 代码调用对应检索器或工具 | 最灵活，可处理复杂路由逻辑和语义匹配 | 延迟和成本较高；依赖 LLM 分类稳定性 | LangChain `RunnableBranch`；LlamaIndex `RouterQueryEngine` |
| 嵌入相似性路由 | 计算查询与预设“路由示例语句”的向量相似度 | 定义路由描述并向量化 → 计算查询与各路由描述的余弦相似度 → 选择最相似路由并调用处理链 | 延迟低，不依赖 LLM 分类 | 只能基于文本相似度，复杂逻辑处理能力弱 | LangChain 自定义 `route` 函数 + `RunnableLambda` |

## 六、LangChain 与 LlamaIndex 查询路由比较

| 框架 | 路由方式 | 核心组件 | 特点 |
|---|---|---|---|
| LangChain | 基于 LLM 的意图识别 | `classifier_chain`、`RunnableBranch`、LCEL 管道 | 用 `prompt | llm | parser` 构建分类器，`RunnableBranch` 类似 if-elif-else 选择分支 |
| LangChain | 嵌入相似性路由 | `embeddings.embed_query`、`cosine_similarity`、`RunnableLambda` | 计算查询与路由描述的相似度，选最相似路由，延迟低 |
| LlamaIndex | 基于 LLM 的意图识别 | `RouterQueryEngine`、`QueryEngineTool`、`Selector` | 将数据源或策略包装为 Tool，用 `LLMSingleSelector` 或 `PydanticSingleSelector` 让 LLM 选择 |
| LlamaIndex | 语义路由 | 融合在 LLM 意图识别中 | 没有独立向量相似度路由组件，而是让 LLM 理解 Tool 描述语义后决策，更灵活 |

## 七、查询翻译与查询路由的关系比较

| 维度 | 查询翻译 | 查询路由 |
|---|---|---|
| 关注点 | 单个查询如何改写、分解、扩展 | 查询应该走哪条路径、用哪个数据源或组件 |
| 解决问题 | 查询与文档之间的语义鸿沟 | 多数据源、多组件、多策略的调度问题 |
| 典型技术 | 提示工程、Multi-query、Step-Back、HyDE | LLM 意图识别、嵌入相似性路由 |
| 组合方式 | 可先翻译，再路由；也可先路由，再对子查询翻译 | 实际系统常将两者组合使用 |
| 目标 | 提升检索输入质量 | 提升系统效率和答案准确性 |

## 八、结论

查询重构与分发是检索优化中的关键预处理阶段。查询翻译通过提示工程、多查询分解、退步提示和 HyDE，从不同角度弥合用户提问与文档之间的语义鸿沟；查询路由则通过 LLM 意图识别或嵌入相似性路由，将查询智能分发到最合适的数据源、组件或提示模板。两者不是替代关系，而是互补关系：翻译提升单个查询的质量，路由决定查询的处理路径。实际系统中，常先路由再翻译，或先翻译再路由，需要根据数据源数量、查询复杂度、延迟和成本要求综合选择。示例表明，提示工程生成结构化排序指令可以解决 SelfQueryRetriever 无法处理“时间最短的视频”的问题；而 LangChain 与 LlamaIndex 在路由实现上各有侧重，前者提供更细粒度的 LCEL 与自定义路由能力，后者通过 Tool + RouterQueryEngine 提供更高层抽象。
