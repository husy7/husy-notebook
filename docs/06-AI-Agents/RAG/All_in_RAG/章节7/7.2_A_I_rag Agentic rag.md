# Agentic RAG：传统RAG、Graph RAG与Agentic RAG比较

> 依据《第七章 高级RAG架构（拓展选修篇）第二节 Agentic RAG：让 RAG 具备自主决策能力》整理，重点比较传统RAG局限、Agentic RAG核心能力、架构与工具生态、三种模式、三种范式差异与协同、端到端实践、效果评估与失败边界。

## 一、从传统RAG到Agentic RAG的范式跃迁

| 维度 | 传统RAG | Agentic RAG |
|---|---|---|
| 检索定位 | pipeline 中的固定步骤 | Agent 可随时调用、反复调用、以不同方式调用的工具 |
| 流程 | 用户提问 → 查询编码 → 单次检索 → 拼接上下文 → LLM 生成 → 返回答案 | Plan → Retrieve → Critique → Refine 循环，质量足够才 Generate |
| 决策能力 | 无，无论检索质量如何都强行生成 | 自主规划检索策略、评估质量、多轮迭代推理 |
| 反馈机制 | 无 | 完整的反思-改写循环 |
| 工具选择 | 无 | 自主多工具选择 |
| 适用问题 | 简单事实型 | 复杂多步、多源整合、需要动态决策的开放域问答 |

## 二、传统RAG四大核心局限

| 局限 | 表现 | 案例 |
|---|---|---|
| 无检索质量感知 | 检索到噪声/无关文档仍强行生成 | 问“苹果最新财报”，检索器返回水果种植文档 |
| 无法动态调整策略 | 第一次检索失败后无法换方向 | 关键词搜不到，不会自动换语义检索 |
| 无工具选择能力 | 所有问题用同一种检索方式 | 简单 FAQ 和复杂推理走同一个 pipeline |
| 信息融合浅层 | 拿到部分信息就开始生成 | 需要 A+B+C 三点，只检索到 A、B 就生成了答案 |

> 根源：传统 RAG 把“检索”当作固定函数调用，而非需要决策的认知过程。

## 三、Agentic RAG 四个核心能力

| 能力 | 说明 | 与传统技术的关系 |
|---|---|---|
| 查询规划 Plan | 面对复杂问题，Agent 将其拆解为多个子问题，决定检索顺序 | 是第4章多查询分解的升级版：不仅分解，还决定先查哪个、后查哪个 |
| 检索决策 Decide | 自主判断何时检索、用什么工具、如何组织参数 | 超越第4章预定义 Router：基于当前状态和历史做动态推理 |
| 质量自评 Critique | 检索完成后，评估结果的相关性和充分性 | 传统 pipeline 对检索结果“照单全收”，Agent 会问“信息够不够回答问题？” |
| 迭代改写 Refine | 质量不足时，分析失败原因后针对性改写 | 与第4章“盲猜式改写”不同，这是诊断式改写 |

## 四、Agentic RAG 核心架构三层比较

| 层级 | 组件 | 说明 |
|---|---|---|
| 决策层 | LLM Agent | 查询分析、工具选择、质量评估、答案合成 |
| 工具层 | vector_search / web_search / kg_query / database_query | Agent 按需调用，每个工具有明确适用场景 |
| 数据层 | 向量数据库 / Web 引擎 / 知识图谱 / 结构化数据库 | 多种异构知识源，Agent 自主路由 |

### 核心循环

```text
Plan（规划查询） → Retrieve（执行检索） → Critique（评估质量）
                                              ├── 足够 → Generate（生成答案）
                                              └── 不足 → Refine（诊断改写）→ Plan
```

## 五、工具生态比较

| 工具 | 适用场景 | 对应章节 |
|---|---|---|
| `vector_search` | 语义相似性检索、开放域问答 | 第3章 |
| `web_search` | 实时信息、最新事件 | 本节新增 |
| `kg_query` | 实体关系、多跳推理 | §7.1 Graph RAG |
| `database_query` | 结构化数据、统计分析 | 第4章 Text2SQL |

## 六、Agentic RAG 三种模式比较

| 模式 | 架构 | 适用场景 | 特点 |
|---|---|---|---|
| 模式一：单 Agent + 工具调用 | 一个 LLM Agent 在 ReAct 循环中自主决定何时调用检索工具 | 大多数场景 | 最实用 |
| 模式二：多 Agent 协作 | 规划 Agent 分解问题，多个检索 Agent 并行检索不同来源，评判 Agent 评估质量，生成 Agent 合成答案 | 超复杂任务 | 分工明确，复杂度高 |
| 模式三：Agent + 知识图谱协同 | Agent 用 `kg_query` 查询知识图谱实体关系，同时用 `vector_search` 检索非结构化文档 | 需要两种 RAG 范式互补 | 结合 Graph RAG 与 Agentic RAG |
| 实践要点 | 不要为了 Agentic 而 Agentic | 简单问题用传统 RAG 即可 | Agentic RAG 价值在于多步推理、多源整合、动态决策的复杂查询 |

## 七、三种范式核心差异比较

| 维度 | 传统 RAG | Graph RAG（§7.1） | Agentic RAG（本节） |
|---|---|---|---|
| 检索次数 | 单次 | 单次/多次（预定） | 动态多次（自主决定） |
| 检索策略 | 固定（向量相似度） | 固定（图遍历+社区检测） | 动态（Agent 自主选择） |
| 反馈机制 | 无 | 有限 | 完整的反思-改写循环 |
| 工具选择 | 无 | 受限 | 自主多工具选择 |
| 适用问题 | 简单事实型 | 多跳关系推理 | 复杂多步、多源整合 |
| 延迟/成本 | 低 | 中 | 较高 |

### 三者协同：混合架构

| 查询类型 | 推荐路径 |
|---|---|
| 简单事实型 | 传统 RAG |
| 多跳关系型 | Graph RAG |
| 复杂推理型 | Agentic RAG，按需调用 `vector_search`、`kg_query`、`web_search` |

> 这与第九章智能查询路由思路一致——Agentic RAG 用动态自主决策替代了预定义的路由规则。

## 八、端到端实践：基于 LangGraph 的最小实现

| 组件 | 说明 |
|---|---|
| 配套代码 | `code/C7/agentic_rag/` |
| 构建方式 | 使用 LangGraph 构建 Agent 状态图，精确控制决策循环，比 ReAct 自由循环更可控、更易调试 |
| 状态图 | `START → analyze_query → retrieve → critique ─┬→ generate → END`；`↑ └─ refine ←┘`（质量不足时） |
| 关键状态 | `query`、`retrieval_history`、`collected_docs`、`critique_result`、`iteration`、`max_iterations` |

### 核心节点比较

| 节点 | 作用 | 关键逻辑 |
|---|---|---|
| `analyze_query` | Agent 先分析，再检索 | 分析问题复杂度，决定检索策略，输出优化后的初始查询 |
| `retrieve` | 执行检索 | 调用工具获取文档 |
| `critique` | 检索质量自评 | 输出 `relevance_score`、`sufficiency_score`、`is_sufficient`、`failure_reason`、`suggested_rewrite` |
| `refine` | 诊断式改写 | 基于失败原因针对性改写，而非盲猜 |
| 条件路由 | 决定下一步 | 迭代超限 → `max_iter`；信息充分 → `generate`；不足 → `refine` |

## 九、完整 Agentic 轨迹示例

问题：“2024年诺贝尔物理学奖得主的研究与化学奖得主的研究之间有什么联系？”

| 轮次 | Agent 决策 | 评估 | 改写逻辑 |
|---|---|---|---|
| Round 1 | 检索物理奖信息 | 充分性 4/10，缺化学奖信息 | 角度偏差 → 新增化学奖查询 |
| Round 2 | 检索化学奖信息 | 充分性 5/10，缺技术关联 | 偏表面 → 增加“深度学习 神经网络 AlphaFold” |
| Round 3 | 检索技术关联 | 充分性 9/10 ✅ | 停止检索，生成答案 |

> 轨迹展示了三个关键行为：自主规划分步检索、语义层面的质量评估、诊断式改写。

## 十、与传统RAG的效果对比

| 指标 | 传统 RAG | Agentic RAG | 提升 |
|---|---|---|---|
| Context Recall | 0.62 | 0.91 | +47% |
| Context Precision | 0.71 | 0.83 | +17% |
| Faithfulness | 0.85 | 0.89 | +5% |
| Answer Relevance | 0.68 | 0.88 | +29% |
| 平均延迟 | ~1.2s | ~6.8s | — |
| 平均 Token 消耗 | ~800 | ~4,200 | — |

> Agentic RAG 在 Context Recall 上提升最显著（多轮迭代补全缺失信息），代价是延迟和 Token 消耗显著增加——适合质量优先于速度的场景。

## 十一、失败边界分析

| 场景 | 表现 | 教训 |
|---|---|---|
| 知识库确实缺少某方面信息 | Agent 反复改写也无法创造出不存在的内容；多轮检索无果后强制生成，输出部分准确但回避核心 | 好的 Agent 应在多轮检索无果时诚实告知信息不足，而非强行生成不够可靠的答案 |
| 示例 | 查询“Hopfield 网络的能量函数在蛋白质折叠预测中的具体应用” | Round 1 无相关文档 → 改写 → Round 2 泛泛介绍 → 改写 → Round 3 Max Iterations 强制生成 |

## 十二、与课程其余章节的衔接

| 章节 | 关系 |
|---|---|
| 第4章 检索优化 | Multi-Query、HyDE、查询路由是 Agentic RAG 的原子能力——Agent 用它来编排和执行，而非替代它 |
| 第6章 RAG 评估 | 评估三元组完全适用；Agentic RAG 需额外关注检索效率（平均几轮达标）、决策准确性（是否过早停止或过度检索）、改写有效性（改写后质量是否显著提升） |
| §7.1 Graph RAG | 两种互补的高级 RAG 范式；最强大的系统是二者融合：Agent 用 `kg_query` 调用知识图谱，需要结构化推理时走 Graph RAG，需要灵活决策时走 Agentic RAG |

## 十三、选择建议

| 需求 | 推荐方案 | 理由 |
|---|---|---|
| 简单事实型问答 | 传统 RAG | 延迟低、成本低 |
| 多跳关系推理 | Graph RAG | 图结构支持结构化多跳推理 |
| 复杂多步推理、多源整合、动态决策 | Agentic RAG | 自主规划、质量自评、诊断式改写 |
| 企业级最强系统 | 三者混合架构 | 查询分类器按类型路由到传统 RAG、Graph RAG 或 Agentic RAG |
| 生产环境 | 单 Agent + 单工具起步，逐步增加工具 | 设置最大迭代次数，做好日志监控，注意失败边界 |

## 十四、结论

Agentic RAG 标志着 RAG 从“检索作为固定步骤”到“检索作为 Agent 可决策工具”的范式跃迁。传统 RAG 存在无检索质量感知、无法动态调整策略、无工具选择能力、信息融合浅层四大局限；Agentic RAG 通过查询规划、检索决策、质量自评、迭代改写四个核心能力，实现 Plan → Retrieve → Critique → Refine 的自主循环。其架构分为决策层、工具层、数据层，工具生态包括 `vector_search`、`web_search`、`kg_query`、`database_query`，并有单 Agent、多 Agent、Agent + 知识图谱三种模式。与传统 RAG、Graph RAG 相比，Agentic RAG 动态多次检索、自主选择工具、具备完整反思-改写循环，适合复杂多步、多源整合场景。效果对比显示，Agentic RAG 在 Context Recall 和 Answer Relevance 上提升显著，但延迟和 Token 消耗也大幅增加。实践中需注意失败边界：知识库确实缺少信息时，应诚实告知信息不足，而非强行生成。最终，最强大的企业级 RAG 系统往往是传统 RAG、Graph RAG 与 Agentic RAG 的混合架构，按查询复杂度动态路由。
