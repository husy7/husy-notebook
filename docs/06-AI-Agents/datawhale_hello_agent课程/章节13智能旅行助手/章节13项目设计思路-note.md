## 一、整体设计哲学

### 核心问题
如何将前十二章所学知识（框架、工具、记忆、协议等）**融会贯通**，构建一个**完整可用的应用**，而非零散的 Demo。

### 设计主线
从第一章的简单原型 → 完整的多智能体 Web 应用。核心转变在于：

| 维度 | 第一章原型 | 本章完整应用 |
|------|-----------|-------------|
| 架构 | 单 Agent 循环 | 4 Agent 分工协作 |
| 数据 | Python 字典 | Pydantic 模型 + TS 类型 |
| 工具 | 直接函数调用 | MCP 协议集成 |
| 界面 | 命令行 | 前后端分离 Web 应用 |
| 功能 | 生成文字行程 | 地图可视化/预算/编辑/导出 |

## 二、架构设计思路

### 2.1 四层分离架构

```
前端层 (Vue3+TS) → 后端层 (FastAPI) → 智能体层 (HelloAgents) → 外部服务层
```

**设计原则**：每层职责单一，层间通过标准化接口（HTTP/JSON/MCP）通信。

### 2.2 关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 前后端分离 | 是 | 独立开发/部署/测试，可扩展移动端 |
| 数据类型同步 | Pydantic ↔ TypeScript 手动对齐 | 保持前后端数据结构一致 |
| 工具集成方式 | MCP 协议 | 标准化、可扩展、Agent 可自主调用 |
| 多 Agent 还是单 Agent | 多 Agent（4个） | 任务分解、提示词简洁、便于调试维护 |

## 三、数据模型设计思路

### 3.1 设计演进：字典 → Pydantic

**为什么要从字典迁移？**
1. **字段名不统一**：不同 API 返回格式各异（`lng` vs `longitude`）
2. **缺乏类型安全**：`price="60"`（字符串）不会立即报错，运行时才暴露
3. **维护困难**：新增字段需修改多处代码

### 3.2 自底向上的模型设计原则

```
Location（最基础）
  ↑ 被组合
Attraction / Meal / Hotel（基础实体）
  ↑ 被组合
DayPlan（单日行程）
  ↑ 被组合
TripPlan（完整计划）
```

**核心思想**：从最原子的概念开始定义，逐层组合成复杂结构。每层模型简单、可独立测试。

### 3.3 Pydantic 关键机制的应用

| 机制 | 应用场景 | 示例 |
|------|---------|------|
| `Field(...)` | 必填字段 | `name: str = Field(..., description="景点名称")` |
| `Field(default=...)` | 可选/默认值 | `ticket_price: int = Field(default=0, ge=0)` |
| `field_validator` | 格式转换 | `"16°C" → 16`（温度字符串转整数） |
| 嵌套模型 | 组合关系 | `location: Location` |
| `List[Type]` | 集合关系 | `attractions: List[Attraction]` |

### 3.4 跨语言类型同步

```
Python (Pydantic)          TypeScript (interface)
Location.longitude    ↔    Location.longitude
Attraction.ticket_price ↔  Attraction.ticket_price?
```

**注意**：`Optional[X]` 对应 `X?`，`List[X]` 对应 `X[]`。

## 四、多智能体协作设计思路

### 4.1 为什么不用单 Agent？

| 问题 | 单 Agent 表现 | 多 Agent 解决方式 |
|------|--------------|------------------|
| 工具调用限制 | SimpleAgent 每次只能调一个工具，需手动管理中间结果 | 每个 Agent 专注一个工具调用 |
| 时间成本 | ReactAgent 串行多轮 LLM 调用，耗时长 | 子任务并行（前三个 Agent 可同时执行） |
| 提示词复杂度 | 需描述所有任务逻辑，难以维护、易出错 | 每个 Agent 提示词短小、职责清晰 |
| 调试困难 | 输出不理想时难以定位问题环节 | 可单独测试每个 Agent 的输出 |

### 4.2 Agent 角色分工

```
AttractionSearchAgent（景点搜索）──→ 调用 MCP: amap_maps_text_search
WeatherQueryAgent（天气查询）────→ 调用 MCP: amap_maps_weather
HotelAgent（酒店推荐）──────────→ 调用 MCP: amap_maps_text_search
PlannerAgent（行程整合）────────→ 无工具调用，纯整合+生成
```

**设计原则**：
1. **单一职责**：每个 Agent 只做一件事
2. **输出可验证**：前三个 Agent 输出结构化数据（JSON），PlannerAgent 整合
3. **提示词极简**：只说清楚"输入 → 工具 → 输出"，不掺杂其他逻辑

### 4.3 协作流程设计

```
用户需求 ──→ [并行] 景点搜索 / 天气查询 / 酒店推荐
                    ↓           ↓           ↓
                查询构建器（_build_planner_query）
                    ↓
                PlannerAgent 整合生成
                    ↓
                Pydantic 解析（TripPlan）
```

**关键设计**：`_build_planner_query` 方法将所有子 Agent 的输出与用户需求**格式化为一个结构化查询**，让 PlannerAgent 能一次性理解全部上下文。

## 五、MCP 工具集成设计思路

### 5.1 为什么不用直接 API 调用？

| 问题 | 直接 API 调用 | MCP 集成 |
|------|-------------|---------|
| Agent 自主性 | 无法让 Agent 自主决策调哪个 API | Agent 通过 `[TOOL_CALL:...]` 自主选择 |
| 参数说明 | 需在提示词中详述每个 API 的参数 | MCP 自动暴露工具 schema |
| 响应解析 | 需手写解析代码，API 变更需修改 | MCP 服务器统一处理 |
| 工具管理 | 每个 API 一个函数，手动注册 | `auto_expand=True` 自动注册全部工具 |

### 5.2 MCP 集成的核心机制

```python
mcp_tool = MCPTool(
    name="amap_mcp",
    command="npx",  # 启动方式
    args=["-y", "@sugarforever/amap-mcp-server"],
    env={"AMAP_API_KEY": settings.amap_api_key},
    auto_expand=True  # 关键：自动发现并注册16个工具
)
```

**`auto_expand=True` 的魔法**：
- 启动 MCP 服务器进程
- 通过 stdin/stdout 通信（JSON-RPC 格式）
- 自动发现服务器提供的所有工具
- 为每个工具创建独立的 Tool 对象
- Agent 添加一个 `mcp_tool`，实际获得 16 个工具

### 5.3 共享 MCP 实例的设计决策

**问题**：3 个 Agent 都需要高德地图工具，每个 Agent 创建独立 MCPTool 实例还是共享？

**决策**：共享同一个实例。

**理由**：
1. **资源节约**：只启动 1 个服务器进程，而非 3 个
2. **API 限流控制**：统一出口，避免超过高德 API 速率限制
3. **配置一致性**：API 密钥等配置只需设置一次

### 5.4 Unsplash 为什么不走 MCP？

**设计判断**：Unsplash 图片搜索**不需要 Agent 的智能决策**，只是简单的数据增强（为景点配图），因此在 API 路由层直接调用服务类即可。

**判断标准**：
- 需要 Agent 自主决策是否调用 → 封装为 Tool/MCP
- 固定流程中的数据增强 → 直接在业务代码中调用

## 六、前端设计思路

### 6.1 技术栈选择依据

| 技术 | 角色 | 选择理由 |
|------|------|---------|
| Vue 3 | 框架 | Composition API 组织逻辑清晰 |
| TypeScript | 类型 | 与后端 Pydantic 类型对齐，减少运行时错误 |
| Ant Design Vue | UI 组件 | 丰富的表单/卡片/统计组件，开发效率高 |
| Vite | 构建 | 快速冷启动，开发体验好 |
| Axios | HTTP | 拦截器统一处理日志/错误 |

### 6.2 前后端类型对齐设计

**核心思想**：后端 Pydantic 模型和前端 TypeScript interface **结构完全一致**，API 响应无需手动转换。

```typescript
// 前端类型定义
export interface TripPlan {
  city: string
  days: DayPlan[]
  budget?: Budget  // 对应 Pydantic 的 Optional[Budget]
}
```

**好处**：
1. IDE 代码补全和类型检查
2. 后端数据结构变更时前端立即发现（编译错误）
3. 减少字段拼写错误

### 6.3 用户体验设计

| 功能 | 设计思路 |
|------|---------|
| 加载进度条 | 无法获取真实进度，用**模拟进度**+状态文案，让用户知道系统在工作 |
| 行程编辑 | 深拷贝保存原始数据，支持取消恢复；移动/删除后重新初始化地图 |
| 导出功能 | html2canvas → Canvas → 图片/PDF；地图 Canvas 嵌套兼容性问题用**隐藏地图**的简化方案 |
| 侧边导航 | `scrollIntoView({ behavior: 'smooth' })` 平滑滚动到锚点 |

## 七、关键功能实现思路

### 7.1 预算计算

**在哪计算**：PlannerAgent（后端），而非前端。

**为什么在后端**：LLM 在生成行程时已掌握景点门票、酒店价格、餐饮标准等信息，直接要求 LLM 在 JSON 输出中包含预算字段，避免前端重复计算逻辑。

**提示词设计**：
```
"7. 包含预算信息，根据景点门票、酒店价格、餐饮标准和交通方式估算"
```

### 7.2 行程编辑的状态管理

```
editMode（是否编辑中）
originalPlan（深拷贝的原始计划，用于取消恢复）
tripPlan（当前计划，编辑时直接修改）
```

**深拷贝的必要性**：JavaScript 对象是引用类型，直接赋值会使两个变量指向同一对象，修改会相互影响。

### 7.3 导出功能的妥协设计

**理想方案**：包含地图的完整截图。
**实际方案**：导出时暂时隐藏地图，只导出文字内容。

**原因**：`html2canvas` 处理嵌套 Canvas（地图）存在兼容性问题，且高德地图 Canvas 渲染机制复杂。

**替代方案（书中提到的改进方向）**：
1. 使用高德静态地图 API
2. 前后端分离导出，后端合并
3. 使用 Puppeteer 无头浏览器截图
4. 简化导出内容

## 八、设计原则总结

### 8.1 核心设计原则

1. **自底向上建模**：从最简单的概念（Location）开始，逐层组合
2. **单一职责**：每个 Agent 只做一件事，每个函数只做一件事
3. **类型即文档**：Pydantic/TypeScript 类型定义本身就是最好的文档
4. **标准化集成**：MCP 协议统一工具接入，避免硬编码 API 调用
5. **优雅降级**：导出功能的简化方案、温度解析的容错处理（`return 0`）

### 8.2 可迁移的设计模式

| 模式 | 应用场景 |
|------|---------|
| 任务分解 → 多 Agent | 复杂任务（旅行规划）拆分为独立子任务 |
| 共享资源实例 | 多个 Agent 需要访问同一外部服务时 |
| 自底向上建模 | 任何有层级关系的数据结构设计 |
| 模拟进度反馈 | 无法获取真实进度的长耗时操作 |
| 深拷贝 + 恢复 | 可取消的编辑操作 |

## 九、延伸思考

本章的旅行助手是一个**模板项目**，其设计思路可复用于：
- 智能购物助手（商品搜索/比价/推荐/生成清单）
- 智能学习助手（课程搜索/进度规划/资源推荐/学习计划）
- 智能健康助手（症状查询/医院推荐/饮食规划/健康报告）

**关键可复用组件**：
- 多 Agent 协作框架（角色分工 + 查询构建器）
- MCP 工具共享机制
- Pydantic ↔ TypeScript 类型同步流程
- 前端交互模式（进度条/编辑/导出/锚点导航）
