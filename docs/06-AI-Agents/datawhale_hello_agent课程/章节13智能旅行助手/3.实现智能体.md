# 多智能体旅行规划系统代码详解
这是一个基于 **hello_agents 框架** 构建的多智能体协作系统，用于自动生成旅行计划。下面我将从架构设计、核心组件、执行流程等维度详细解析。
---
## 一、整体架构概览
```
                    ┌─────────────────┐
                    │  TripRequest    │  用户请求(城市/日期/偏好)
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
┌───────────────┐  ┌───────────────┐  ┌───────────────┐
│ 景点搜索Agent  │  │ 天气查询Agent  │  │ 酒店推荐Agent  │
│ (带MCP工具)   │  │ (带MCP工具)   │  │ (带MCP工具)   │
└───────┬───────┘  └───────┬───────┘  └───────┬───────┘
        │                  │                  │
        └──────────────────┼──────────────────┘
                           ▼
                ┌─────────────────────┐
                │   行程规划Agent       │  (无工具,纯推理)
                │  整合信息生成JSON计划  │
                └──────────┬──────────┘
                           ▼
                ┌─────────────────────┐
                │   TripPlan 结构化对象 │
                └─────────────────────┘
```
**设计模式：** 类似“流水线+汇总”式的多智能体协作，前三个Agent是“信息采集员”，第四个Agent是“总规划师”。

## 二、核心组件解析
### 1. 四个专用Agent（各自独立提示词）
| Agent | 职责 | 是否带工具 | 关键设计点 |
|-------|------|-----------|-----------|
| 景点搜索专家 | 按关键词搜景点 | ✅ 高德地图 | 提供精确工具调用示例 |
| 天气查询专家 | 查城市天气 | ✅ 高德地图 | 只调用 `maps_weather` |
| 酒店推荐专家 | 搜酒店 | ✅ 高德地图 | 限定关键词为“酒店/宾馆” |
| 行程规划专家 | 整合生成计划 | ❌ 无 | 输出严格JSON |
**提示词设计亮点：**
```python
ATTRACTION_AGENT_PROMPT = """...
你必须使用工具来搜索景点!不要自己编造景点信息!
...
[TOOL_CALL:amap_maps_text_search:keywords=历史文化,city=北京]
"""
```
- **强制工具调用**：通过强语气指令“不要编造”，防止LLM幻觉出虚假景点
- **格式示例**：通过 few-shot 示例让LLM学会 `[TOOL_CALL:工具名:参数]` 的精确格式
- 这说明该框架采用**文本协议式工具调用**（而非原生 function calling），提示词中的格式约束至关重要
### 2. 共享MCP工具
```python
self.amap_tool = MCPTool(
    name="amap",
    description="高德地图服务",
    server_command=["uvx", "amap-mcp-server"],  # 通过uvx启动MCP服务器
    env={"AMAP_MAPS_API_KEY": settings.amap_api_key},
    auto_expand=True  # 自动展开子工具
)
```
关键点：
- **只创建一次，三个Agent共享**：避免重复启动MCP服务器进程，节省资源
- `uvx` 是 uv 的包执行器，类似 `npx`，无需预装即可运行 `amap-mcp-server`
- `auto_expand=True` 会把MCP服务器的工具展开为独立可调用工具（如 `amap_maps_text_search`、`amap_maps_weather`）
```python
self.attraction_agent.add_tool(self.amap_tool)
self.weather_agent.add_tool(self.amap_tool)   # 同一个工具实例
self.hotel_agent.add_tool(self.amap_tool)
```
### 3. 行程规划Agent的JSON Schema
PLANNER_AGENT_PROMPT 中内嵌了完整的JSON模板，这是典型的 **“结构化输出约束”** 技巧：
```json
{
  "city": "...", "days": [...], 
  "weather_info": [...],
  "budget": {"total_attractions": 180, "total": 2060}
}
```
- **字段级约束**：如“温度必须是纯数字（不要带°C）”——针对LLM常见错误的预防
- **业务规则**：每天2-3个景点、三餐必须齐全、预算必须汇总
- 这份JSON结构与 `schemas.py` 中的 Pydantic 模型（TripPlan、DayPlan、Attraction等）一一对应

## 三、核心执行流程 `plan_trip()`
这是典型的 **顺序协作（Sequential Workflow）**：
```python
# 步骤1: 搜索景点（注入了工具调用格式）
attraction_query = self._build_attraction_query(request)
attraction_response = self.attraction_agent.run(attraction_query)
# 步骤2: 查询天气
weather_response = self.weather_agent.run(f"请查询{request.city}的天气信息")
# 步骤3: 搜索酒店
hotel_response = self.hotel_agent.run(f"请搜索{request.city}的{request.accommodation}酒店")
# 步骤4: 规划Agent整合生成最终JSON
planner_query = self._build_planner_query(request, attraction_response, weather_response, hotel_response)
planner_response = self.planner_agent.run(planner_query)
# 解析为结构化对象
trip_plan = self._parse_response(planner_response, request)
```
### 一个值得注意的“作弊”技巧
```python
def _build_attraction_query(self, request: TripRequest) -> str:
    query = f"请使用amap_maps_text_search工具搜索...
[TOOL_CALL:amap_maps_text_search:keywords={keywords},city={request.city}]"
```
**代码直接把工具调用指令拼进了用户消息里**！这是因为纯靠提示词约束LLM输出正确格式并不可靠，代码层面直接“演示”给模型看，大幅提高工具调用成功率。这是一种务实的工程妥协。

## 四、鲁棒性设计（三重防护）
### 防护1：初始化异常处理
```python
except Exception as e:
    traceback.print_exc()
    raise  # 初始化失败直接抛出，快速失败
```
### 防护2：JSON解析容错 `_parse_response()`
采用**三级降级解析策略**：
```python
if "```json" in response:      # 优先：标准markdown JSON块
elif "```" in response:          # 其次：无语言标记的代码块
elif "{" in response and "}" in response:  # 最后：裸JSON对象
```
这个设计很实用，因为LLM输出格式不稳定，可能是：
```json
​```json {...} ​```    ← 最规范
​``` {...} ​```        ← 少了json标记
直接输出 {...}          ← 最随意
```
### 防护3：兜底方案 `_create_fallback_plan()`
当整条链路失败时，生成一个“占位计划”：
```python
attractions=[
    Attraction(
        name=f"{request.city}景点{j+1}",   # 占位名称
        location=Location(longitude=116.4 + i*0.01 + j*0.005, ...)  # 假坐标
    )
]
```
⚠️ **注意**：兜底方案中的经纬度是硬编码的北京附近坐标（116.4, 39.9），对其他城市完全不适用，这是生产环境需要改进的点。

## 五、单例模式
```python
_multi_agent_planner = None
def get_trip_planner_agent() -> MultiAgentTripPlanner:
    global _multi_agent_planner
    if _multi_agent_planner is None:
        _multi_agent_planner = MultiAgentTripPlanner()
    return _multi_agent_planner
```
**为什么用单例？** 因为初始化成本高——需要：
- 启动MCP服务器进程（uvx）
- 建立4个Agent实例
- 连接LLM
单例保证Web服务（如FastAPI）中只初始化一次，后续请求复用。

## 六、代码质量评价
### ✅ 优点
1. **职责分离清晰**：每个Agent单一职责，提示词针对性强
2. **资源复用**：共享MCP工具、单例模式
3. **健壮性强**：三级JSON解析 + 兜底计划，全链路try/except
4. **可观测性**：每步都有进度打印，方便调试
5. **结构化输出**：Pydantic模型保证类型安全
### ⚠️ 可改进之处
| 问题 | 建议 |
|------|------|
| 兜底计划的假坐标 | 应返回错误或提示用户重试，而非假数据 |
| 顺序执行较慢 | 三个采集Agent可**并行执行**（asyncio/threading），天气/景点/酒店查询互不依赖 |
| 解析依赖文本格式 | 可改用LLM的 **原生 function calling / JSON mode** |
| `_build_planner_query` 中的列表编号错误 | 要求编号有两个"3"，无"4"（笔误，第4条写成`3.`） |
| 全程print而非logging | 生产环境应使用 `logging` 模块 |
| 上下文长度风险 | 三个Agent的原始响应直接拼接给planner，若结果过长可截断或预处理提取关键字段 |

## 七、一句话总结
> 这段代码展示了一个**务实的多智能体工程实践**：用“角色化提示词 + 强制工具调用格式 + 共享MCP工具 + 流水线协作 + 多级容错”的方式，将一个复杂任务（旅行规划）分解为可独立完成、可容错降级的子任务，最终通过规划Agent汇总为结构化输出。适合作为学习多智能体系统设计的入门参考。
