## 3. 代码模块拆解（一张图看懂所有类）

我把这几十个类分成 **4大家族**，记住他们的后缀就能分清职责：

| 家族分类 | 命名特征（后缀） | 代表类 | 核心职责 |
| :--- | :--- | :--- | :--- |
| **👨‍💻 请求家族** | `*Request` | `TripRequest`<br>`POISearchRequest` | **“顾客的点菜单”**。定义前端必须传什么参数给后端。 |
| **🧩 零件家族** | 无特定后缀 | `Location`<br>`Attraction`<br>`Hotel`<br>`WeatherInfo` | **“后厨的食材”**。用于系统内部流转、拼装行程的基本单元。 |

## 4. 新手必须死记的 3 个字段写法（避坑指南）

在写代码处理数据时，看见下面这几种写法，脑子要立刻反应过来：

- **写法一：`Field(...)`**（三个点）
  - `city: str = Field(..., description="城市")`
  - **翻译**：`...` 是 Python 里的“必填”标识。前端如果不传 `city` 字段，程序直接报错，**绝不手软**。

- **写法二：`Optional[str] = None`**（可选空）
  - `free_text_input: Optional[str] = Field(default="")`
  - **翻译**：用户可以填，也可以不填。不填时默认给空字符串 `""`。
  - **新手大坑**：你在代码里使用它之前，**必须**判断 `if free_text_input:`，否则可能会因为空值导致报错。

- **写法三：`List[Attraction] = []`**（空列表默认值）
  - `attractions: List[Attraction] = Field(default=[])`
  - **翻译**：默认是个空列表。遍历它时不需要判空（因为 `[]` 也是合法的），但如果你想取 `attractions[0]`，**必须**先 `if attractions:` 判断有值，否则报 `IndexError`。

## 5. 高级小技巧（让你看起来像老手）

### 🔧 技巧一：温度清洗器（`@field_validator`）
```python
@field_validator('day_temp', mode='before')
def parse_temperature(cls, v):
    return int(v.replace('°C', ''))  # "28°C" → 28
```
- **妙用**：外部地图API返回的温度常常带后缀（如 `"28°C"`），但这个没法做数学计算。这个装饰器会在数据进入系统的**一瞬间**把 `"°C"` 扒掉，转成纯数字 `28`。以后你遇到类似的需求（比如清洗手机号中的 `-` 号），照猫画虎即可。

### 📦 技巧二：模型嵌套（俄罗斯套娃）
注意看它们的包含关系，这是整个系统的骨架：
- `TripPlan` 包含 → 多个 `DayPlan`
- `DayPlan` 包含 → 多个 `Attraction` + 多个 `Meal` + 一个 `Hotel`
- `Attraction` 包含 → 一个 `Location`

**写代码时的直观感受**：你获取了一个 `TripPlan` 对象后，想拿第一天的第一个景点名称，代码链就是：
`plan.days[0].attractions[0].name`
**这就是结构化数据的魅力，比用字典（dict）写 `["days"][0]["attractions"]` 要清晰一万倍！**

## 6. 响应模型的统一格式（规范很重要）

注意看，所有 `*Response` 类（如 `TripPlanResponse`）长得很像：

```python
class XxxResponse(BaseModel):
    success: bool          # 必定有：是否成功
    message: str = ""      # 必定有：提示消息
    data: Optional[Xxx]    # 核心数据，如果没有就返回 null
```

- **为什么这么设计？** 这是业界最佳实践。前端前端只需要固定判断 `response.success` 是否为 `True`，如果是，就去取 `data`；如果否，就弹出 `message` 里的错误提示。**前端同学再也不用猜你这接口返回的报错字段叫 `error` 还是 `msg` 了。**
