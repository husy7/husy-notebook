# 项目代码总结

## 一、项目概述

基于 **HelloAgents「Agent + 工具链」** 的 LLM 应用：**PDF 智能问答助手**个人修改版本。

- **功能**：上传 PDF 解析、向量化入库，经 **RAG（检索增强生成）** 智能问答；记录**多类型学习记忆**，支持学习回顾与报告生成。
- **形态**：Gradio Web 界面（`http://127.0.0.1:7860`），启动即自动初始化助手。
- **技术栈**：Python · Gradio（流式）· Qdrant · Ollama（OpenAI 兼容 LLM）· sentence-transformers · Neo4j（可选）· SQLite · pydantic v2 · concurrent.futures · Git/GitHub。

## 二、核心架构

`main_.py` 的 `PDFLearningAssistant` 组合两个工具：**RAGTool**（问答）+ **MemoryTool**（记忆）。

```
main_.py
 ├─ RAGTool    → rag/pipeline.create_rag_pipeline → storage/qdrant_store + embedding
 └─ MemoryTool → memory_manmager.MemoryManager    → memory_types/{working,episodic,semantic}
```

- 所有工具继承 `base.py::Tool`（ABC），统一采用模板方法 **`run()` → 校验 → `_execute()`**。
- 顶层模块间用绝对导入（项目根在 `sys.path`）；规范约束：PEP8、行宽 ≤120、函数 ≤50 行、`if` 嵌套 ≤3、中文 docstring。

## 三、RAG 问答链路

流程：**文档解析 → 分块 → 嵌入 → Qdrant 向量化 → 相似度检索 → LLM 增强生成**。

- **解析**：markitdown 统一解析 PDF/Office/图片/音频。
- **嵌入**：sentence-transformers（本地 all-MiniLM）/ dashscope / TF-IDF 三级回退。
- **向量**：Qdrant，384 维、余弦距离。
- **高级检索（按需）**：默认基础检索；结果为空或平均分 < 0.3 时才启用 **MQE（Query 扩展）+ HyDE（假设性文档）** 提升召回，避免普通问题无谓触发多次 LLM。

## 四、记忆系统

四类记忆：**工作 / 情景 / 语义 / 感知**。

- 工作记忆：内存 list（易失）；情景/语义：Qdrant + SQLite（持久）；语义可加 Neo4j 图（可选，不可用自动降级为向量-only）。
- 支持：添加、检索、摘要、**整合**（高重要性短期记忆提为长期）、**多策略遗忘**（重要性 / 时间 / 容量）。

## 五、关键问题与优化（做了什么、为什么改、结果如何）

以下均为实际遇到并解决的问题，数据来自实测。

### 1. 修复运行阻断（可用性）
| 问题 | 处理 | 结果 |
|---|---|---|
| PDF 二进制字节被当正文入库，问答出现乱码 | 补装 markitdown 的 PDF 依赖 + 拦截二进制内容 | 乱码消失，文本正常抽取 |
| Neo4j 不可用时直接抛异常，拖垮整体初始化 | 改为可选项，不可用自动降级为向量-only | 跨环境可稳定启动 |
| 多处越界相对导入导致 MQE/HyDE 静默失效 | 改为顶层绝对导入 | 高级检索真实生效 |
| `core/agent.py` 导入被改坏（绝对导入） | 恢复为正确的相对导入 | 恢复正常 import |

### 2. 补全隐藏能力（记忆工具白名单）
- **问题**：`validate_parameters` 白名单不完整，整合/遗忘/统计等 6 个动作经统一入口调用一律报错。
- **处理**：白名单与真实实现强一致，并补动作级必填校验。
- **结果**：记忆的增删改查/整合/遗忘全部打通，可作为 Agent 记忆能力复用。

### 3. 体验优化
- **流式输出**：逐 token 生成，回答首字即现（原为整段生成完才返回）。
- **按需高级检索**：普通问题走基础检索，疑难才触发 MQE/HyDE。
- **后台加载**：`load_pdf` 异步化，上传文档界面不再卡死。

### 4. 性能定位与并发优化
- **定位方法**：分步实测——embedding（CPU 计算）单条仅 **~13ms**；Qdrant（网络 IO）单次约 **1s**；大头是 Ollama 在 CPU 上生成长文本。
- **优化**：将 MQE/HyDE 的多次 LLM 调用**并发**、多查询**批量嵌入 + Qdrant 并发查询**。
- **结果**：多查询检索 **4.89s → 2.27s（约 2 倍提速）**。
- **边界**：本地 torch 受 GIL，CPU 计算应**批量化**而非线程化；直接对初始化盲目做线程并行实测反而变慢（56s→62s，单例锁竞争）。

### 5. 模型接入与推理调优
- **问题**：为提速切换小模型时，实测多个本地模型"设置生成长度上限即返回空"，且默认 13 万超大上下文拖慢甚至卡死推理。
- **处理**：禁用思考（`think=False/LLM_THINK=0`）+ 限制上下文窗口（`num_ctx=2048`）+ 调大超时；对比后选定能正常配合限长的模型。
- **结果**：单次问答从 30s+ 降至约 3-20s（覆盖冷启动波动），不再因上下文过大卡死。

### 6. 初始化提速
- **问题**：`create_rag_pipeline` 每次初始化都重复建 Qdrant 索引，切用户等同流程变慢。
- **处理**：改用 Qdrant 连接单例复用。
- **结果**：同进程二次初始化 **31.2s → 23.3s**。

## 六、工程化

- **依赖**：`requirements.txt`（gradio / qdrant-client / markitdown[pdf] / sentence-transformers 等）。
- **配置安全**：`.env.example` 安全模板（仅占位值、零真实密钥）；`.gitignore` 排除 `.env` 与数据目录，密钥不上传。
- **文档**：`README.md`（功能改进）、`CHANGELOG.md`（逐项记录与验证）。
- **版本管理**：项目已推送至 GitHub 私有仓库，分支 `main`。

## 七、遗留与后续方向

- **遗留**：工作记忆易失（进程重启即丢）；仓库存在重复文件（根级 `qdrant_store.py`、`mem.py`）；Neo4j 凭据需在服务端改密启用。
- **方向**：LLM 生成提速（GPU / 换行为正常的小模型）；检索重排（cross-encoder）；文档解析与检索并行化进一步降低延迟。
