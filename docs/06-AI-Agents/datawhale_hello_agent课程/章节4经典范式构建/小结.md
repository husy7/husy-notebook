# 第四章 智能体经典范式构建 · 小结

> 从零实现 ReAct、Plan-and-Solve、Reflection 三种经典范式，理解智能体"思考与行动"的组织差异与选型策略。

## 三范式速查表

| 范式 | **ReAct** | **Plan-and-Solve** | **Reflection** |
| :--- | :--- | :--- | :--- |
| **核心公式** | 思考 ⇄ 行动 ⇄ 观察（循环） | 先全量规划 -> 再逐步执行 | 执行 -> 反思 -> 优化（迭代） |
| **一句话人设** | **"边想边干，走一步看一步"** | **"谋定而后动，计划不改"** | **"先干为敬，睡前复盘"** |
| **决策流特征** | **交错式**<br>每步依赖上一步外部反馈 | **串行分离式**<br>执行时不再思考 | **双阶段式**<br>初稿产出后自我批改 |
| **对错误的反应** | **即时止损**（此路不通换条路） | **一错皆错**（计划静态，某步失败则全盘崩溃） | **延迟修正**（本轮错，下轮改） |
| **算力/时间成本** | 中等（轮数多，单步短） | 低（一次规划，批量执行） | 高（每轮 2N+1 次调用） |
| **最佳战场** | 开放世界、不确定环境、需外部工具 | 固定流程、可分解任务、确定性操作 | 高质量代码/报告、逻辑推演 |

## 三范式组合口诀

> **Plan** 拆大任务（粗粒度），  
> **ReAct** 管现场（细粒度），  
> **Reflection** 悟（进化度）。

## 记忆锚点

- **ReAct** = **"知行合一"**（知即行，行即知）  
- **Plan-and-Solve** = **"纸上谈兵"**（兵推完美，但战场无常）  
- **Reflection** = **"吾日三省吾身"**（省完再战，战完再省）

## 范式选型决策树

```
任务需求？
├─ 需外部工具/实时信息/路径不确定 → ReAct
├─ 结构清晰、可分解为明确步骤 → Plan-and-Solve
├─ 对结果质量/可靠性要求极高 → Reflection（可叠加在前两者之上）
└─ 复杂任务 → 组合：Plan 拆任务 → ReAct 执行 → Reflection 优化
```

## 综合习题

### 习题1（章末原题）：三范式本质区别与组合

- Q1：三种范式在"思考"与"行动"的组织方式上有什么本质区别？
  A1：ReAct 交错式（每步思考-行动-观察耦合）；Plan-and-Solve 串行分离式（先全量规划再执行，执行时不思考）；Reflection 双阶段式（初稿产出后引入事后反思迭代回路）。

- Q2：设计"智能家居控制助手"选哪种范式？为什么？
  A2：推荐 Plan-and-Solve 为基础架构 + ReAct 处理异常。理由：① 智能家居控制流程结构化（开灯/调温/拉窗帘是独立步骤），适合先规划后执行；② 但用户需求可能模糊或设备状态变化，执行阶段用 ReAct 动态适配。Reflection 可用于学习用户习惯后优化策略。

- Q3：能否组合三范式？设计混合架构。
  A3：可以。混合架构：Plan-and-Solve 拆解用户意图为设备控制计划 → ReAct 逐步执行并处理设备反馈 → Reflection 在夜间复盘当日执行记录优化用户习惯模型。适用场景：需要长期学习和自适应的复杂个人助手。

### 习题2（章末原题）：输出解析鲁棒性

- Q1：正则解析 ReAct 输出的脆弱性？
  A1：① LLM 输出格式微小偏差（多空格、换行、中英文冒号）即匹配失败；② Action 嵌套方括号（`Search[query[filter]]`）截断错误；③ LLM 生成多余文本干扰匹配。

- Q2：更鲁棒的解析方案？
  A2：① 用 OpenAI Function Calling/Structured Output 原生支持，LLM 直接返回 JSON；② 用 JSON 模式 + Pydantic 模型校验；③ Few-shot 示例引导格式 + 宽松解析器兜底。

- Q3：修改代码用 JSON 格式对比？
  A3：将 Action 改为 `{"tool": "Search", "input": "query"}` JSON 格式。优点：解析稳定、支持嵌套参数、易扩展。缺点：部分模型 JSON 遵循率低、Token 略增、调试时不如纯文本可读。

### 习题6（章末原题）：电商客服智能体设计

- Q1：选哪种范式（组合）？
  A1：混合架构。Plan-and-Solve 拆解流程（理解理由→查订单→判政策→发邮件）→ ReAct 执行查订单/物流（需调用工具）→ Reflection 处理争议决策（置信度低时自我反思）。

- Q2：需要哪些工具？
  A2：① `QueryOrder`（查订单信息和物流状态）；② `QueryPolicy`（查退款政策知识库）；③ `SendEmail`（生成并发送回复邮件）；④ `CalculateRefund`（计算退款金额）。

- Q3：如何设计提示词确保决策合规又友好？
  A3：系统提示词嵌入公司退款政策核心条款 + 决策准则（"优先保障公司利益，但保持用户友好"）；用 Few-shot 示例展示合规且友好的回复模板；Reflection 阶段从"政策合规性"和"用户满意度"双维度审视。

- Q4：上线后风险与应对？
  A4：风险：① 误判退款（过度批准/拒绝）→ 设人工审核兜底+决策日志可追溯；② 提示词注入攻击（用户伪造理由）→ 输入消毒+系统提示词隔离；③ 政策变更 → 政策知识库可热更新，不硬编码。降低手段：灰度发布+A/B测试+实时监控决策准确率。

### 习题7（章末原题）：提示词工程对比

- Q1：ReAct 与 Plan-and-Solve 提示词设计差异如何服务各自逻辑？
  A1：ReAct 提示词强制 `Thought:/Action:` 格式，注入工具清单和历史轨迹，服务"边想边干"的交错循环；Plan-and-Solve 规划提示词强制输出 Python 列表，服务"一次性全量规划"；执行提示词包含完整计划+历史结果，服务"严格按计划执行"。

- Q2：Reflection 中角色设定对行为的影响？
  A2：角色设定直接决定反思深度。"极其严格、对性能有极致要求"→ 反思聚焦算法效率，能发现 O(n√n) 瓶颈并建议筛法；改为"注重可读性的开源维护者"→ 反思聚焦命名、注释、代码风格，不会触及算法层。角色即反思视角的控制器。

- Q3：Few-shot 示例的效果？
  A3：加入完整 Thought-Action-Observation 成功案例，能显著提升模型对格式的遵循率，减少解析失败。尤其对能力较弱的模型效果明显，但会增加 Token 消耗，需在效果与成本间平衡。
