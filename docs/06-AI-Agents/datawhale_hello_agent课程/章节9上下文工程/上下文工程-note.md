## 一、核心概念

### 1.1 什么是上下文工程

**定义**：上下文工程（Context Engineering）是在每一次模型调用前，以可复用、可度量、可演进的方式，拼装并优化输入上下文的工程化方法。

**与提示工程的区别**：

| 维度 | 提示工程 | 上下文工程 |
|------|---------|-----------|
| 关注点 | 如何编写指令 | 如何策划与维护最优信息集合 |
| 范围 | 系统提示的写法 | 提示+工具+历史+外部数据等一切进入上下文窗口的内容 |
| 时间跨度 | 单轮/短时 | 长时程、跨多次推理轮次 |
| 核心问题 | 句式措辞 | 什么样的上下文配置最可能产出期望行为 |

### 1.2 为什么上下文工程重要

**上下文腐蚀（Context Rot）**：随着上下文窗口中的tokens增加，模型准确回忆信息的能力反而下降。

**注意力预算**：LLM像人类一样有有限的工作记忆容量，每新增一个token都消耗注意力预算的一部分。

**架构约束**：
- Transformer的n²两两注意力关系随上下文增长被"拉薄"
- 训练数据中短序列更常见，模型对长程依赖建模能力有限
- 位置编码插值技术扩展了序列长度但牺牲精确性

## 二、有效上下文的解剖学

### 2.1 核心组件

**系统提示**：
- ❌ 过度硬编码：复杂脆弱的if-else逻辑，维护成本高
- ❌ 过于空泛：只有宏观目标，缺少具体信号
- ✅ 平衡点：分区组织（Role/Policies/Tools/Output），追求"最小必要信息集"

**工具设计原则**：
- 职责单一、相互低重叠
- 接口语义清晰
- 对错误鲁棒
- 入参描述明确无歧义
- 构建"最小可行工具集（MVTS）"

**示例（Few-shot）**：
- 精挑细选多样且典型的示例
- 不罗列所有边界条件
- 好的示例胜过千言万语

### 2.2 上下文检索策略

**JIT（Just-in-time）上下文**：
- 维护轻量化引用（文件路径、URL等）
- 运行时通过工具动态加载
- 认知模式：像人类用文件系统、书签按需提取

**渐进式披露（Progressive Disclosure）**：
- 每一步交互产生新上下文，指导下一步决策
- 文件大小暗示复杂度、命名暗示用途、时间戳暗示相关性
- 按层构建理解，只在工作记忆中保留"当前必要子集"

**混合策略**：
- 前置加载少量高价值上下文保证速度
- 允许智能体按需自主探索
- 边界取决于任务动态性与时效要求

## 三、长时程任务三大策略

### 3.1 压缩整合（Compaction）

- **定义**：对话接近上限时进行高保真总结，用摘要重启新上下文窗口
- **保留**：架构性决策、未解决缺陷、实现细节
- **丢弃**：重复的工具输出与噪声
- **调参**：先优化召回，再优化精确度

### 3.2 结构化笔记（Structured Note-taking）

- **定义**：智能体以固定频率将关键信息写入上下文外持久化存储，后续按需拉回
- **价值**：以极低上下文开销维持持久状态与依赖关系
- **典型应用**：TODO列表、NOTES.md、关键结论/依赖/阻塞项索引

### 3.3 子代理架构（Sub-agent Architectures）

- **思想**：主代理负责高层规划，子代理在干净上下文窗口中深挖，仅回传凝练摘要（1,000-2,000 tokens）
- **好处**：关注点分离，适合并行探索的复杂研究/分析任务

### 3.4 策略选择经验法则

| 策略 | 适用场景 |
|------|---------|
| 压缩整合 | 需要长对话连续性的任务 |
| 结构化笔记 | 有里程碑/阶段性成果的迭代式开发 |
| 子代理架构 | 复杂研究分析，能从并行探索获益 |

## 四、ContextBuilder：GSSC流水线

### 4.1 核心数据结构

**ContextPacket**：候选信息包
- content：信息内容
- timestamp：时间戳
- token_count：Token数量
- relevance_score：相关性分数（0.0-1.0）
- metadata：元数据（type、priority等）

**ContextConfig**：配置管理
- max_tokens：最大token数（默认3000）
- reserve_ratio：系统指令预留比例（默认0.2）
- min_relevance：最低相关性阈值（默认0.1）
- recency_weight + relevance_weight = 1.0

### 4.2 GSSC四阶段

**Gather（汇集）**：
- 系统指令：最高优先级，relevance_score=1.0
- 记忆系统检索：limit=10，min_importance=0.3
- RAG检索：limit=5，min_score=0.3
- 对话历史：默认最近5条
- 容错机制：每个外部源用try-except包裹

**Select（选择）**：
- 综合分数 = relevance_weight × 相关性 + recency_weight × 新近性
- 相关性计算：Jaccard相似度（可替换为向量相似度）
- 新近性计算：指数衰减模型，24小时内高分
- 贪心算法：按分数降序填充至token上限
- min_relevance过滤低质量信息

**Structure（结构化）**：
```
[Role & Policies] 系统指令
[Task] 用户查询
[Evidence] RAG检索结果
[Context] 对话历史+记忆
[Output] 输出格式指导
```

**Compress（压缩）**：
- 分区压缩：保持结构完整性
- 完整保留优先，token不足时截断
- 保留至少50 tokens
- 标记"[... 内容已压缩 ...]"

## 五、NoteTool：结构化笔记

### 5.1 存储格式

**Markdown + YAML混合格式**：
```markdown
---
id: note_20250119_153000_0
title: 项目进展 - 第一阶段
type: task_state
tags: [refactoring, phase1, backend]
created_at: 2025-01-19T15:30:00
updated_at: 2025-01-19T15:30:00
---

# 正文内容（Markdown格式）
```

**索引文件**（notes_index.json）：集中管理元数据，支持快速检索

### 5.2 笔记类型

| 类型 | 用途 |
|------|------|
| task_state | 阶段性进展和状态 |
| conclusion | 重要结论和发现 |
| blocker | 阻塞问题（优先级最高） |
| action | 下一步行动计划 |
| reference | 重要参考资料 |
| general | 通用笔记 |

### 5.3 核心操作

- **create**：创建笔记
- **read**：读取笔记（解析YAML+Markdown）
- **update**：更新笔记（自动更新updated_at）
- **search**：关键词搜索（支持类型/标签过滤）
- **list**：列出笔记（按更新时间倒序）
- **summary**：统计摘要（总数、类型分布、最近更新）
- **delete**：删除笔记

## 六、TerminalTool：即时文件系统访问

### 6.1 四层安全机制

**第一层：命令白名单**
- 只允许只读命令：ls, cat, head, tail, find, grep, wc, sort, uniq, cut, awk, sed, pwd, cd等
- 禁止任何修改系统的操作

**第二层：工作目录沙箱**
- 只能访问指定workspace及其子目录
- 禁止通过`..`逃逸
- 禁止访问系统文件（如/etc/passwd）

**第三层：超时控制**
- 默认30秒，防止无限循环

**第四层：输出大小限制**
- 默认10MB，防止内存溢出

### 6.2 典型使用模式

**探索式导航**：
```python
terminal.run({"command": "ls -la"})       # 查看根目录
terminal.run({"command": "cd src"})        # 进入目录
terminal.run({"command": "find . -name '*service*.py'"})  # 搜索文件
terminal.run({"command": "cat user_service.py"})          # 查看内容
```

**数据分析**：
```python
terminal.run({"command": "head -n 5 sales.csv"})           # 预览
terminal.run({"command": "wc -l *.csv"})                   # 统计
terminal.run({"command": "tail -n +2 sales.csv | cut -d',' -f2 | sort | uniq -c"})  # 聚合
```

**日志分析**：
```python
terminal.run({"command": "tail -n 50 app.log | grep ERROR"})       # 最新错误
terminal.run({"command": "grep ERROR app.log | awk '{print $4}' | sort | uniq -c | sort -rn"})  # 错误分布
```

## 七、长程智能体实战：代码库维护助手

### 7.1 三层架构

```
┌─────────────────────────────────┐
│     ContextBuilder (上下文构建)   │
│   GSSC流水线 + 智能筛选           │
├─────────────────────────────────┤
│  工具层                          │
│  MemoryTool │ NoteTool │ TerminalTool │
├─────────────────────────────────┤
│  基础设施                        │
│  文件系统 │ 记忆存储 │ 笔记系统    │
└─────────────────────────────────┘
```

### 7.2 核心设计模式

**模式化预处理**：
- explore模式：自动查看项目结构
- analyze模式：检查代码复杂度和TODO
- plan模式：加载最近的task_state笔记

**自动笔记创建**：
- 检测到"问题/bug/错误/阻塞"关键词 → 自动创建blocker笔记
- 检测到"计划/下一步/任务"关键词 → 自动创建action笔记

**相关性分级**：
```python
relevance_map = {
    "blocker": 0.9,      # 阻塞问题优先级最高
    "action": 0.8,       # 行动计划次之
    "task_state": 0.75,  # 任务状态
    "conclusion": 0.7    # 结论
}
```

### 7.3 关键特性

1. **跨会话连贯性**：NoteTool保持多天任务连贯
2. **智能上下文管理**：ContextBuilder自动汇集相关笔记
3. **即时文件访问**：无需预先索引，按需探索
4. **自动化知识管理**：自动检测并记录问题和计划
5. **人机协作**：支持手动干预和指导

- 支持手动编辑和干预

## 九、关键公式与算法

**综合评分**：
```
combined_score = relevance_weight × relevance_score + recency_weight × recency_score
```

**Jaccard相似度**（相关性计算）：
```
Jaccard(A, B) = |A ∩ B| / |A ∪ B|
```

**指数衰减**（新近性计算）：
```
recency_score = e^(-decay_factor × age_hours / 24)
```

**Token估算**：
```
tokens ≈ 中文字符数 + 英文单词数 × 1.3
```

## 对比与选型

### 上下文管理策略对比

| 策略 | 适用场景 | 优点 | 缺点 | 典型实现 |
|------|---------|------|------|---------|
| **压缩整合（Compaction）** | 需要长对话连续性的任务，如多轮代码调试、持续性对话 | 保持对话流连贯，实现简单；能自动提炼关键信息 | 可能丢失细节；压缩质量依赖LLM能力；不适用于需要精确历史引用的场景 | ContextBuilder 的 Compress 阶段 |
| **结构化笔记（Structured Note-taking）** | 有里程碑、阶段性成果的迭代式开发/研究，如项目重构、文献综述 | 持久化存储，跨会话保持；低上下文开销；人类可读可审计 | 需要额外维护；检索依赖于笔记质量和索引设计；可能产生信息冗余 | NoteTool（Markdown + YAML） |
| **子代理架构（Sub-agent）** | 复杂研究/分析任务，需要并行探索多个子问题 | 关注点分离，主代理聚焦综合；子代理拥有干净上下文；并行加速 | 系统复杂度高；通信开销大；子代理结果需要有效整合 | 多智能体框架（如 Hello-Agents 扩展） |
| **即时检索（JIT）** | 需要探索大型文件系统或外部数据源，任务动态性强 | 避免预加载全部数据；信息实时最新；节省token预算 | 运行时探索可能较慢；需要设计良好的工具和引导策略 | TerminalTool + 工具调用 |

### 工具选型指南

| 工具 | 核心用途 | 最佳实践 | 注意事项 |
|------|---------|---------|---------|
| **ContextBuilder** | 统一上下文管理，实现 GSSC 流水线 | 用于每次LLM调用前自动构建最优上下文；配置合理 token 预算和权重 | 相关性计算在生产中应替换为向量相似度；需监控 token 使用率 |
| **NoteTool** | 结构化持久笔记，长时程状态追踪 | 用于记录任务状态、阻塞、结论、行动计划；按类型和标签组织 | 笔记数量增长后需定期归档；检索性能优化 |
| **TerminalTool** | 即时文件系统访问和命令执行 | 用于代码库探索、日志分析、数据预览；配合安全沙箱使用 | 严格限制命令白名单和工作目录；控制输出大小 |

### 综合选型决策树

```
任务是否需要长时间跨会话保持一致？
├── 是 → 是否涉及大量外部文件/代码/数据探索？
│   ├── 是 → 组合使用：NoteTool（持久状态）+ TerminalTool（即时探索）+ ContextBuilder（上下文整合）
│   └── 否 → 主要使用 NoteTool + ContextBuilder，必要时 MemoryTool
└── 否 → 任务是否复杂且可分解？
    ├── 是 → 考虑子代理架构，每子代理使用独立 ContextBuilder
    └── 否 → 直接使用 ContextBuilder + 必要的工具（Memory/RAG/Terminal）
```
